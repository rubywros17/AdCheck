# Rule Judge 파이프라인 비결정성(non-determinism) 관찰 기록

같은 상품 페이지를 여러 번 분석했을 때, 결과가 실행마다 달라지는 사례를 모아두는 기록이다.
`AnalysisResultResolver`의 재사용 캐시(reuseTtl)는 "동일 요청이면 동일 결과"를 보장해줄 뿐,
캐시가 없는 첫 분석·캐시 만료 후 재분석에서는 이 불안정성이 그대로 드러난다.

각 항목은 실제 DB(`analyses.result_json`)에서 확인한 원본 값만 기록한다 — 추측이나 재구성된
값은 넣지 않는다.

## 관찰 기록

문구들이 매 실행마다 통째로 누락됐을 가능성을 시사한다. 규칙판정(AI#3)의 판정 흔들림보다 한
단계 앞선, 더 근본적인 문제로 보인다 — Claim 추출 자체의 재현성(recall 안정성)을 별도로
점검할 필요가 있다.

### 2026-09-22 · **입력을 완전히 고정해도 재현된다** (대조 실험)

앞의 사례는 "같은 페이지를 다시 분석"한 것이라 페이지 쪽 변화(지연 로딩, 배너 교체 등)가
섞였을 가능성을 배제할 수 없었다. 이번엔 **OCR 텍스트를 파일로 고정해 두 번 제출**해서 입력
변수를 완전히 제거했다(이미지 없이 `texts`만 전송 → OCR 단계 자체가 돌지 않음).

| 페이지 | 같은 입력 2회 불일치 | 참고: 다른 OCR 엔진 간 불일치 |
|---|---|---|
| chosunhnb.com | **4건** | 3건 |
| www.grsmall.co.kr | **5건** | 4건 |
| vitahouse.co.kr | 0건 | 0건 |
| happytori.kr | 1건 | 4건 |

*(불일치 = sourceText 집합의 대칭차. 4개 중 3개에서 "같은 입력끼리의 차이"가 "다른 엔진 간
차이"와 같거나 더 컸다.)*

chosunhnb.com 실제 출력 — **입력 텍스트가 글자 하나까지 동일한데** 결과가 이렇게 갈렸다:

- run1(5건): `간 건강에 도움을 줄 수 있는 실리마린과…` / `실리마린이 간 건강을 지키는 데…` /
  `간 건강에 도움을 줄 수 있음` / `에너지 대사에 필요` / `간 건강에 도움을 줄 수 있음`
- run2(4건): `실리마린이 간 건강을 지키는 데…` / `간 건강에 도움을 줄 수 있는 실리마린과…` /
  `밀크씨슬추출물의 대표 성분이며 1정당 130mg 함유…` / `탄수화물, 지방, 단백질 대사에 관여하여…`

run2에서만 나온 Claim 2건, run1에서만 나온 Claim 2건이다.

또 happytori.kr에서는 **문구가 완전히 같은 Claim에 카테고리가 다르게 붙었다** —
`내장지방면적 감소`·`엉덩이둘레 감소`가 한 번은 `FUNCTION_EXCEED`, 다른 번은
`MEDICINE_CONFUSION`으로 판정됐다. 추출 단계가 아니라 **규칙 판정 단계에서도** 흔들린다는 뜻이다.

**의미**: 이 편차는 OCR 엔진 선택(Gemini↔Vision) 같은 상류 변경의 영향보다 크다. 즉 지금
단계에서 두 산출물을 비교해 우열을 가리는 실험은 이 노이즈에 묻힌다 — **비교 실험을 하려면
반복 측정이 필수**이고, 제품 관점에서는 이 비결정성 자체가 OCR 교체보다 우선순위가 높다.

### 2026-09-23 · 단계별로 떼어내 측정한 결과 — 추출은 해결, 판정은 92%

전체 파이프라인은 1회에 Gemini 13~16콜이 들어 반복 측정에 부적합했다. 단계별로 분리해 싸게
재는 테스트 두 개를 만들어(`ClaimExtractionStabilityTest` 1회 1콜,
`RuleJudgeStabilityTest` 규칙수×반복) 편차의 발생지를 나눴다.

**모델 쪽 노브는 전부 막혀 있다는 것부터 확인했다.** *(2026-09-27 정정 — 사실과 다르다.
`temperature`와 `thinkingConfig`는 지정할 수 있다. 다만 지정해도 편차가 줄지 않는다는 결론은
유지된다. 아래 2026-09-27 기록 참고.)* Gemini 3.x는 공식 문서가
`temperature`/`topP`/`topK`를 "모든 요청에서 제거하라"고 명시하고, 대안으로 제시된
`thinkingLevel`은 이 모델에서 400으로 거부된다(`Unknown name "thinkingLevel" at
'generation_config'`). 즉 편차를 줄일 방법은 프롬프트뿐이다.

| 단계 | 조치 | 결과 |
|---|---|---|
| Claim 추출(AI#1) | 성분·함량 문장을 3분류로 명문화 | 안정도 **60% → 100%** |
| 규칙 판정(AI#3) C05 | 함량 표기 판단 기준 명시 | 흔들림 **해소** |
| 규칙 판정 전체 | — | **92%** (경계 케이스 상존) |

추출 단계에서 흔들린 문구 2건은 모두 "성분 설명인지 효능 주장인지" 경계에 있었고, 기준을
적어주자 사라졌다 — **모호해서가 아니라 규칙이 비어 있어서** 생긴 편차였다는 뜻이다.

**남은 편차의 성격**은 셋으로 갈린다:

1. **기준 미기재** — 위 두 건처럼 명문화로 해소 가능. 발견될 때마다 같은 절차(측정 → 지점
   특정 → 명문화 → 재측정)를 반복하면 된다.
2. **진짜 문맥 의존** — 문장만으로 판단이 안 되는 경우. 이건 흔들림이 아니라
   `REVIEW_REQUIRED`로 수렴하는 게 정상이고, 실제로 그렇게 동작한다.
3. **판단 근거 자체가 없는 경우** — `C11_SUB_INGREDIENT_FUNCTION`은 주원료/부원료 구분이
   필요한데 원료 확정이 안 되면 근거 없이 판정하게 된다. 실측 15건 전부 원료 확정 0건이었으므로
   운영에서도 이 상태다. **이건 프롬프트가 아니라 원료·제품 확정률 문제**다.

**대표 규칙 선정이 편차를 증폭한다는 점도 확인했다.** `mostSevere()` 자체는 결정적이지만
(규칙 순서가 ruleCode 정렬로 고정), MATCHED 규칙 중 **하나만** 골라 카테고리·위험도·근거를
전부 결정하므로, 규칙 12개 중 11개가 동일해도 흔들린 1개가 대표였으면 사용자에게는 전혀 다른
결과로 보인다. 판정 92% 안정인데 최종 화면이 훨씬 불안정해 보이는 이유다. 이를 완화하려면
여러 건을 노출해야 하는데 카드가 과도해져, 지금은 그대로 두기로 했다.

### 2026-09-27 · 6개 상품 페이지 교차 측정 — **한 페이지 결과를 파이프라인의 성질로 읽으면 안 된다**

앞 기록들은 전부 페이지 한 곳에서 잰 값이다. 이번에 **서로 다른 상품 페이지 6개를 같은
조건으로** 재면서, 그렇게 얻은 수치가 페이지를 바꾸면 그대로 무너진다는 것이 확인됐다.

전날 `i-hi.co.kr/product_no=111`에서 표기 정규화 후 안정도 60%를 재고 "해결"로 적었는데,
같은 페이지가 다음 날 0%로 나왔다.

#### 측정 방법

고정 입력을 페이지마다 만들었다 — 상품 페이지 HTML을 받아 익스텐션 추출기
(`page-extractor.ts`)와 같은 규칙으로 텍스트·이미지를 뽑고, 그 이미지를 Google Vision으로
한 번 OCR해 동결했다. 입력 전체가 상수라야 편차의 발생지를 AI로 특정할 수 있다.

수집기가 익스텐션을 제대로 흉내 내는지는 111번(익스텐션 실물 입력이 있는 페이지)으로
대조했다.

| | 익스텐션 실물 | 수집기 |
|---|---|---|
| 이미지 | 24장 | **24장 (동일)** |
| OCR 글자수 | 12,480 | 12,536 (GCV 지터 0.4%) |
| 텍스트 | 146개 / 3,644자 | 109개 / 5,530자 |

이미지·OCR은 사실상 같고 텍스트는 다르다 — 정적 HTML이라 CSS로 숨겨진 메뉴가 들어오고
JS로 펼쳐지는 가격·옵션이 빠진다. **입력의 77%가 OCR**이라 지배적인 쪽은 충실하며, 6개
페이지를 모두 같은 방식으로 수집했으므로 페이지 간 비교는 동일 조건이다.

#### 결과 (6개 페이지 × 5회, 표기 정규화까지 적용된 상태)

| 페이지 | OCR | 회차별 Claim | 안정도 | claim별 출현율 |
|---|---|---|---|---|
| 111 아이뉴트리움 | 23장 | `[1,4,3,4,3]` | 0% | 50% |
| 97 | 33장 | `[4,4,5,8,5]` | 38% | 65% |
| 12 아이그램 | 26장 | `[6,7,5,5,8]` | 17% | 52% |
| 14 아이모어 | 19장 | `[7,9,3,5,5]` | 18% | 53% |
| 30 아이브레이니 | 20장 | `[4,3,3,3,2]` | 17% | 50% |
| 66 아이리톨 | 24장 | `[1,2,1,1,1]` | 0% | 60% |

**평균 안정도 15%.**

#### 지표를 바꿔야 한다 — "안정도"는 표본에 휘둘린다

안정도는 `교집합 / 합집합`, 즉 **5회 전부에 나온 것만** 센다. 66번처럼 claim이 2건뿐인
페이지는 하나만 빠져도 0%가 된다. 이 지표로는 페이지끼리 비교가 안 된다.

claim별 **출현율**(각 claim이 5회 중 몇 번 나왔는지의 평균)로 바꿔 재니 6개 페이지가 전부
**50~65%**로 일정했다.

> **claim 하나가 5회 중 평균 2.5~3.3회 나온다.** 페이지를 바꿔도 변하지 않는다. 이것이
> 파이프라인의 실제 성질이고, 앞으로 이 지표로 기준선을 잡는다.

#### 앞 기록 정정 — 모델 설정은 지정할 수 있다

2026-09-23 기록에 *"모델 쪽 노브는 전부 막혀 있다"*고 적었는데, 직접 요청을 보내 확인한
결과 사실과 다르다. 다만 **지정해도 편차는 줄지 않는다**는 결론은 유지된다.

| 설정 | 결과 |
|---|---|
| `temperature: 0.0` | **HTTP 200** — 요청에 실려 나가는 것까지 로그로 확인 |
| `thinkingConfig.thinkingBudget: 0` | HTTP 400 (이 모델은 0으로 끌 수 없음) |
| `thinkingConfig.thinkingBudget: 1 / 128 / 512` | HTTP 200 |
| `thinkingConfig.thinkingBudget: -1` (동적) | HTTP 200 |
| `thinkingLevel` | HTTP 400 — `Unknown name "thinkingLevel"` (앞 기록대로) |

`thinkingConfig`는 API가 아는 필드다. 오타 필드를 넣은 대조군은
`Unknown name "thinkingConfigXX" ... Cannot find field`라는 **다른** 오류가 났다.

**그런데 thinking은 이미 꺼져 있었다.** 토큰 사용량을 같이 찍어 보니 설정 없는 현재
운영 상태에서 `thoughtsTokenCount = 0`이고, budget을 줘도 0이며, `-1`을 줘야 1,810토큰이
쓰인다. 즉 thinking budget은 편차를 **줄일 수단이 아니라 늘릴 수단**이다.

`temperature: 0`으로 같은 측정을 다시 돌린 결과도 개선이 없었다(111번 `[6,4,3,13,2]`,
97번 `[3,6,4,3,7]`). 프롬프트 조립에도 순서가 흔들릴 자료구조가 없어
(`ProductContentExtractionService`는 `LinkedHashSet` 하나뿐) 같은 입력이면 같은 프롬프트가
나간다. **모델 설정으로 잡을 수 있는 층위는 전부 확인했고, 편차는 그 바깥에 있다.**

#### 출력 형식을 바꿔 보고 되돌린 기록

claim을 자유 서술 대신 **줄 번호로 받는** 방식을 시험했다. 원료표(`labelLineGroups`)가 이미
쓰고 있는 방식을 claim에도 적용하는 것으로, 문장을 우리 코드가 조립하므로 지어내기·이어
붙이기·표기 차이가 구조적으로 불가능해진다.

측정 전에 유지/되돌림 기준을 먼저 정했다(출현율 ≥75% 유지 / <65% 되돌림).

| 페이지 | 기준선 출현율 | 줄 번호 방식 | |
|---|---|---|---|
| 111 | 50% | 30% | −20%p |
| 97 | 65% | 38% | −27%p |
| 12 | 52% | 56% | +4%p |
| 14 | 53% | 29% | −23%p |
| 30 | 50% | 80% | +30%p |
| 66 | 60% | 29% | −31%p |
| **평균** | **55%** | **44%** | **−11%p** |

기준 미달로 되돌렸다(커밋하지 않음).

**기계적으로는 완전히 동작했다** — 30회 전부 폴백 0건(모델이 새 형식을 100% 따름), 잘못된
번호로 버린 건 회차당 0~1건, **원문에 없음 0건**. 설계대로 작동했는데 원하던 효과가 안 났다.

해석: 모델이 하던 일이 "문장을 읽고 고르기"에서 **"800줄짜리 번호 목록에서 번호를 세어
짚기"**로 바뀌면서 부기 부담이 얹혔다. 14번에서 claim 0건 회차가 나왔고, 66번은
`[1,2,1,1,1]` → `[6,11,10,7,18]`로 뛰었다 — 문장을 직접 써야 할 때는 신중해지는데 번호만
찍으면 부담 없이 많이 찍는 것으로 보인다.

**원료표에서 같은 방식이 잘 되는 이유**도 이제 설명된다. 원료표는 한 덩어리로 붙어 있는
연속 구간이라 "여기부터 여기까지"로 잡으면 되는데, claim은 800줄에 흩어진 개별 줄을 하나씩
짚어야 한다. 같은 방식이라도 난이도가 다르다.

#### 측정할 때 지킬 것

- **페이지 한 곳으로 판단하지 않는다.** 최소 여러 페이지를 같은 조건으로 재고, 한 페이지만
  잰 값은 그 한계를 명시한 잠정 관찰로만 적는다.
- **합성 데이터의 100%를 해결 근거로 쓰지 않는다.** `ClaimExtractionStabilityTest`(손으로 쓴
  12줄)는 지금도 100%인데, 실제 페이지(프롬프트 4~6만 자)에서는 claim이 2~25건까지 흔들린다.
- **지표는 출현율을 쓴다.** 안정도(교집합/합집합)는 claim 수가 적은 페이지에서 0%로 무너져
  페이지 간 비교가 안 된다.
- **변경 전 기준선을 같은 방법으로 먼저 재 둔다.** 그리고 유지/되돌림 기준을 측정 **전에**
  숫자로 정한다.

측정 도구는 `RealPageExtractionStabilityTest`이며, `STABILITY_INPUTS` 환경변수에 고정 입력
JSON 경로를 쉼표로 이어 주면 페이지별로 재고 마지막에 한 표로 모아 준다.

### 2026-09-27 · AI 다섯 단계를 상류부터 전수 점검 — **편차는 AI#1에만 있다**

*"AI에 문제 있는 부분이 있는지"* 전체를 한 번 보기 위해, 앞 단계가 막히면 뒤 단계 측정이
의미가 없다는 원칙으로 상류부터 순서대로 쟀다.

| 단계 | 결과 |
|---|---|
| **OCR** | 캐시 적중 22/24장, 분석 9.2초 → 5.8초. GCV의 실행 간 글자수 변동이 함께 사라졌다 |
| **AI#1 추출** | **출현율 55% · 원료 확정 0~12건** — 유일하게 원인 미규명 |
| **규칙 판정 (AI 38개)** | 456건 중 432건(95%) 판정. 판정 0건인 것은 `C30_NATURAL_FREE` 하나 |
| **규칙 판정 (정규식 12개)** | **판정 1,032건 전부 보류** — 편차가 아니라 100% 결정론 |
| **RAG** | 질의 4건 × 3회 **순서까지 100% 동일**, 0.5~1.0초 |
| **AI#2 비교·설명** | 5회 모두 다른 문장이지만 내용 일치. 판단 값은 3건 중 1건 뒤집힘(둘 다 "문제 있음" 쪽) |

**편차가 문제인 단계는 AI#1 하나다.** 정규식 12개는 편차가 아니라 구현 범위 문제이고
(→ `docs/troubleshooting.md`), 나머지 셋은 재본 범위에서 이상이 없었다.

#### RAG — 근거가 실제로 맞는다

관련성은 수치로 못 가르므로 문단을 그대로 출력해 읽었다.

```
"매일 한 알로 감기를 예방하세요"
  → 0.706  REVIEW-03 p69  "5 감기 — 건강기능식품의 기능성 범위…"
  → 0.682  REVIEW-03 p80  "감기 등 인체에 작용하는 바이러스에 대한 기능성이 있는…"

"루테인은 눈 건강에 도움을 줄 수 있습니다"
  → 0.729  REVIEW-03 p81  "10. 마리골드꽃추출물 기능성 내용 …"
```

**루테인으로 물었는데 마리골드꽃추출물이 나오는 것이 정답이다** — 루테인의 공식 원료명이
마리골드꽃추출물이고, 임베딩이 그 동의어 관계를 잡아냈다.

다만 한 청크가 `"[원문의 그래프] 60 55 50 45…"` 숫자 나열인데 0.683으로 2순위에 올랐다.
1순위가 제대로 잡혀 당장 문제는 아니지만 청크 품질에 여지가 있다.

#### AI#2 — 문장은 매번 다르지만 같은 말을 한다

```
(1/5회) 루테인의 공식 기능성은 황반색소밀도 유지 및 눈 건강 도움이며, 시력 회복이나
        눈 피로의 완벽한 개선은 인정된 범위를 벗어납니다.                        (58자)
(1/5회) 이 제품의 주원료인 루테인은 황반색소밀도를 유지하여 눈 건강에 도움을 주는
        기능성을 가집니다. 하지만 시력을 직접 회복시키거나…                     (109자)
```

완전 일치 0%(5회 전부 다른 문장), 길이 43~109자. **그러나 다섯 개가 같은 결론을 말한다.**
자유 서술이라 표현이 갈리는 것은 당연하고, 내용은 안정적이다.

#### 표본의 한계 — "이상 없음"은 "문제 없음"이 아니다

| 단계 | 잰 것 | 안 잰 것 |
|---|---|---|
| AI#1 | 상품 페이지 6개 × 5회 | **전부 `i-hi.co.kr` 한 곳** |
| 규칙 판정 | 결정론 12개 × 86문구, AI 38개 × 12문구 각 1회 | AI 규칙의 **편차는 4개만**(3회씩) |
| RAG | 질의 4건 × 3회 | AI#2가 그 근거를 잘 쓰는지는 별개 |
| AI#2 | 문구 3건 × 5회 | 직접 만든 문장. 실제 MATCHED 문구로는 미측정 |

남은 잔여 항목 넷 — `C30_NATURAL_FREE` 판정 0건(미규명), 같은 문구가 3회 중 1회만 MATCHED인
사례(놓침 위험), AI#2 배치 실패 시 호출이 문구 수만큼 늘어나는 구조, RAG 그래프 숫자 청크.

### 2026-09-27 · AI#1 — 원인 후보 다섯을 실측으로 배제했다

출현율 55%의 원인을 찾으려 다섯 층을 차례로 지웠다. **전부 아니었다.**

| 시도 | 결과 |
|---|---|
| `temperature`를 0으로 고정 | 요청에 실려 나가는 것까지 로그로 확인. **효과 없음** |
| thinking 끄기 | 이미 꺼져 있었다 — `thoughtsTokenCount = 0`, budget을 줘도 0, `-1`이라야 켜짐 |
| 출력을 줄 번호로 받기 | 기계적으로는 완벽히 동작(폴백 0건·원문에 없음 0건)했으나 **55% → 44%** |
| 상위 모델로 교체 | 같은 세대 `flash` — **51% → 41%**, 회차당 3.0초 → 26.9초(9배) |
| 프롬프트 조립 점검 | 순서가 흔들릴 자료구조 없음(`LinkedHashSet` 하나) — 결정론적 |

#### 상위 모델이 더 흔들린 이유

`flash`는 claim을 더 많이 뽑는다. 66번 페이지에서 `flash-lite`가 `[1,2,1,2,2]`인데 `flash`는
`[4,5,8,6,5]`였다. **후보가 늘면 경계에 걸친 문장이 많아지고, 그것들이 회차마다 들락거린다.**

원문에 없는 문장이 2건 → 0건으로 준 것도 같은 맥락이다 — 지시는 더 잘 지킨다.
*"상위 모델이 더 못하는"* 게 아니라 *"더 많이 찾는다"*가 정확하다.

#### 합집합이 산술 예측에 못 미친다 — 독립이 아니라는 뜻

3회 합집합을 재봤다. 출현율 55%를 독립 확률로 보면 `1 − 0.45³ = 91%`가 기대되는데 **75%**가
나왔다.

| 페이지 | 회차별 Claim (9회) | 단일 | 합집합 | claim 평균 |
|---|---|---|---|---|
| 111 | `[4,4,1,3,6,13,9,4,1]` | 24% | 60% | 5.0 → 12.7 (2.5배) |
| 97 | `[6,3,4,5,8,5,4,3,2]` | 44% | 63% | 4.4 → 6.3 (1.4배) |
| 66 | `[1,1,2,1,1,2,1,1,2]` | 67% | 100% | 1.3 → 2.0 (1.5배) |
| **평균** | | **45%** | **75%** | 3.6 → 7.0 (1.9배) |

**잘 잡히는 문구는 매번 잡히고, 안 잡히는 문구는 몇 번을 돌려도 계속 놓친다.** 무작위 잡음이
아니라 모델이 일관되게 애매해하는 문장들이 있다는 뜻이고, 횟수를 늘려도 수익이 빠르게 준다.

111번이 2.5배로 튄 것은 13건·9건짜리 이상치 회차를 합집합이 그대로 흡수했기 때문이다.
**잡음이 한 번만 크게 들어와도 합집합은 못 걸러낸다.**

측정 전에 유지/되돌림 기준을 정해뒀고(출현율 ≥75% 유지 / <65% 되돌림) 75%는 경계선이라
켜지 않았다.

#### 남은 해석 — 과제 자체가 열려 있다

지금 AI#1에게 주는 과제는 *"40,000자를 읽고 광고 문구를 골라라"*이고 후보 문장이 600~900개다.
**"이게 광고 문구인가"의 경계가 원래 흐릿하다.** 이 해석이 맞다면 *"원인을 찾아 없앤다"*가
성립하지 않고, 답은 원인 제거가 아니라 설계다 — 재사용 캐시가 그 첫 조각이다.

#### 사용자 체감은 해결됐다 (실측)

```
크롬 추출      146개/24장 두 번 모두 동일, selector 1개만 다름(네이버페이 위젯 id의 타임스탬프)
   ↓
요청 해시      6cef9f9fcf47674b = 6cef9f9fcf47674b
   ↓
백엔드 캐시    3회 연속 같은 분석 · Finding 5건 · 미평가 1건
   ↓
응답 시간      70~96ms (분석 12초의 1/100)
```

**캐시는 편차를 없앤 게 아니라 결과를 고정한다.** 첫 분석 한 번이 7일을 결정하고, 그 한 번은
여전히 55%의 지배를 받는다. 운 나쁘게 위반을 놓친 결과가 캐시되면 7일간 그대로다.
