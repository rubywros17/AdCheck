작업하면서 실제로 겪은 버그/문제와 해결 방법을 기록한다. 같은 실수를 반복하지 않기 위한

## AI 파이프라인 (Claim/원료표시 추출)

### 원료 표시 추출 — 후보 2개 이상이면 null 반환
LLM한테 "원료표에 해당하는 문자열을 새로 만들어서 반환해"라고 시켰더니, 실제 이미지로 테스트할
때 후보(원료표)가 1개면 정상 작동하고 2개 이상이면 아예 `null`을 반환하는 비결정적 문제가
있었다. 반환 타입을 `String` → `List<String>`으로 바꾸고 "하나만 고르지 말고 전부 배열로
반환"하도록 프롬프트를 바꿔서 해결.

### 원료 표시 추출 — 원문 개행 보존으로 콤마 분리가 깨짐
"원문 그대로 옮기라"는 지시를 LLM이 충실히 따르면서, 이미지 폭 때문에 여러 줄로 잘린 OCR
텍스트의 개행 문자까지 그대로 보존한 채 반환했다. 그 결과 `IngredientSplitter`의 콤마 분리
로직이 깨져서 정상 매칭이 안 됐다. LLM한테 문자열을 새로 "생성"시키는 대신, 본문+OCR 텍스트를
줄 단위로 번호 매겨 주고 "원료표에 해당하는 줄 번호만 골라줘"라고 시키는 방식(줄 선택)으로
바꿔서 해결 — 실제 문자열 조립은 코드가 하므로 원문 왜곡 문제가 원천적으로 안 생긴다.

### 광고 문구 속 수치를 원료로 오인식
"성분명+함량 단위가 붙어있으면 다 후보로"라고 시켰더니, "진세노사이드 Rg1+Rb1+Rg3 합
16mg/g"처럼 실제로는 효능 주장·비교용 수치인 걸 원료표로 잘못 뽑는 경우가 있었다. 재구성한
후보 문자열을 곧바로 `IngredientMatchingService`에 넣어보고, 그 안에 하나도 매칭되는 원료가
없으면(전부 UNMATCHED) 후보 자체를 버리도록 해서 해결 — 이미 검증된 매칭엔진을 품질 필터로
재활용.

### Gemini 호출 무한 대기 (타임아웃 미설정)
`GeminiClient`/`GeminiOcrService`에 커넥션/응답 타임아웃이 전혀 설정돼 있지 않아서, 네트워크가
느려지면 스레드가 응답을 무한정 기다리는 버그가 있었다. 단위 테스트로는 절대 안 잡히고, 실제
E2E 테스트 중 앱이 멈춘 걸 보고 `jstack`으로 스레드 덤프를 떠서 `JdkClientHttpRequest
.executeInternal`에 36초 넘게 멈춰있는 스레드를 발견해서야 알았다. `SimpleClientHttp
RequestFactory`에 connect 10초/read 60초 타임아웃을 명시해서 해결.

### Gemini 무료 티어 일일 할당량(500회) 초과
105장 이미지 검증 배치를 돌리다 하루 요청 한도(`GenerateRequestsPerDayPerProjectPerModel-
FreeTier`, 500회)를 다 써서 중간에 API 키를 바꿔서 이어서 처리해야 했다. 근본적으로는 이미지별
개별 호출(1장=OCR 1회+Claim 1회) 구조가 낭비였던 것이라, 이후 OCR을 상품 단위로 배치 호출하고
Claim/원료표시 추출을 프롬프트 하나로 합쳐서 상품당 호출 수를 4회→2회로 줄였다.

## 원료 매칭 알고리즘

### Python→Java 포팅 시 반올림 방식 차이
Python `round()`는 은행반올림(half-even)인데 Java `Math.round()`는 반올림(half-up)이라,
정확히 중간값(0.625 등)인 유사도 점수에서 결과가 갈리는 버그가 있었다. `BigDecimal
.HALF_EVEN`으로 고쳐서 Python 원본과 100% 동일한 결과가 나오도록 맞췄다(288개 케이스 파리티
테스트로 확인).

### v0.2 재작성 시 괄호 제거로 인한 오매칭
Data Contract v0.2 기준으로 원료 매칭을 다시 짜면서, 정규화 함수가 문자열 안의 괄호 내용까지
통째로 지우고 비교하도록 짰었다. 그랬더니 "인삼분말(가루, 과립)(인삼근 70%, 인삼미삼 30%)"
같은 설명형 문자열이 괄호를 지우면 "인삼분말"이 되어, 실제로는 UNMATCHED여야 하는데 동의어사전의
"인삼분말"과 우연히 일치해서 잘못 MATCHED로 판정됐다. 팀원이 준 실제 계산 결과 256건 샘플로
검증하다가 발견 — 괄호는 그대로 보존하고 공백(개행 포함)만 제거하도록 정규화 방식을 바꿔서
해결, 240/256(93.75%) 파리티 확보.

### 팀원 데이터 자체의 시점 불일치 (알고리즘 버그 아님)
파리티 검증 중 `RAW_RECOGNITION_NO`/`UNMATCHED` 조합 16건에서만 계속 불일치가 났다. 원인을
추적해보니 `ingredient_synonyms_v0.2.csv`엔 이미 정확일치 동의어로 등록된 문자열이, 팀원이
사전 계산해준 `product_ingredient_matches_v0.2.csv`엔 UNMATCHED로 남아있는 경우였다 —
동의어사전 쪽이 더 최신이고 계산 결과 파일이 이전 버전 기준으로 만들어진 것으로 보임. 우리
알고리즘 문제가 아니라고 판단해서 이 조합만 검증 대상에서 제외하고, 팀원에게 확인 요청.

## Analysis API / 파이프라인 실행

### `@Async` + `@Transactional` 조합으로 트랜잭션 가시성 버그
분석 요청을 비동기로 처리하도록 바꾸면서, `submit()` 메서드에 `@Transactional`을 걸어놨더니
비동기 스레드가 시작될 때 아직 원본 트랜잭션이 커밋되기 전이라(READ_COMMITTED 격리수준) 방금
저장한 행을 못 찾는 문제가 있었다. DB를 계속 폴링해도 상태가 PENDING에서 안 바뀌는 걸 보고
발견 — `submit()`에서 `@Transactional`을 빼서, 저장이 먼저 커밋된 뒤에 비동기 작업이 시작되게
해서 해결.

### Hibernate `ddl-auto:update`가 고아 컬럼/테이블을 안 지움
엔티티에서 필드를 삭제해도 Hibernate가 실제 DB 컬럼은 그대로 둔다. `detail_text` 등 안 쓰는
컬럼에 남아있던 NOT NULL 제약 때문에 새 저장 로직이 `DataIntegrityViolationException`으로
실패했다. 직접 psycopg2로 접속해서 `ALTER TABLE ... DROP COLUMN`으로 정리해서 해결(로컬
개발용 DB, 테스트 데이터만 있어서 안전하게 진행).

## DB / Flyway 마이그레이션

### Spring Boot 4.x는 `spring-boot-flyway` 모듈이 따로 필요
`org.flywaydb:flyway-core`만 추가하고 실행했더니 Flyway가 아예 동작을 안 했다(로그에 Flyway
관련 언급이 한 줄도 없이 곧바로 Hibernate 스키마 검증에서 "missing table" 에러가 남). Spring
Boot 4.x부터 자동설정이 기술별로 분리된 모듈 구조라(`spring-boot-hibernate`,
`spring-boot-jdbc`처럼), Flyway 자동설정도 `org.springframework.boot:spring-boot-flyway`를
따로 추가해야 활성화됐다.

### `IngredientMatchingService`에 생성자 2개 두니 Spring 빈 생성 실패
DB 조회용 생성자(Repository 4개 받음)와 테스트용 생성자(엔티티 리스트 직접 받음)를 같이
두었더니 "No default constructor found" 에러가 났다. 생성자가 여러 개면 Spring이 어느 걸
autowiring에 쓸지 못 정하는 문제라, DB 조회용 생성자에 `@Autowired`를 명시해서 해결.

### Jackson CSV — record가 CSV의 일부 컬럼만 모델링하면 파싱 실패
CSV에 컬럼이 더 있는데 record는 필요한 몇 개만 필드로 갖고 있으면
`UnrecognizedPropertyException`이 난다(예: `functional_ingredients_v0.2.csv`의
`recognizedAt`/`companyName` 등). `@JsonIgnoreProperties(ignoreUnknown = true)`를 빠뜨릴
때마다 반복해서 겪은 실수 — record가 CSV 전체 컬럼을 안 담을 거면 항상 이 애노테이션을 붙여야
한다.

### `ad_cases_v0.1.csv`의 `ruleCodes` 필드에 부가설명이 섞여 들어옴
콤마로 구분된 규칙 코드 목록인데, "DISC-*" 계열 사례 18건 중 14건은 마지막 코드 뒤에
"; 부가설명문구"가 그대로 붙어있었다(예: `"C01_DISEASE_PREVENTION; 질병정보 구분 필요"`).
콤마로 나눈 뒤 각 토큰을 다시 세미콜론으로 나눠 앞부분만 규칙 코드로 취급하도록 파싱 로직을
추가해서 해결.

### JPA 엔티티의 `protected` 무인자 생성자를 테스트에서 직접 호출 불가
테스트 픽스처를 만들면서 다른 패키지에서 `new IngredientMasterEntity()`를 직접 호출했더니
컴파일 에러(`protected` 접근 제한). `BeanUtils.instantiateClass(Class)`로 접근 제한을 우회해서
인스턴스를 만들고, 필드는 `ReflectionTestUtils.setField()`로 채우는 방식으로 해결.

## Rule Judge (AI#3 — AiRuleEvaluator)

### REVIEW_REQUIRED를 사실상 못 냄 — 지시만 있고 실효가 없었음
프롬프트에 "판단이 애매하거나 근거 자료가 부족하면 REVIEW_REQUIRED로 답하세요"라는 지시를
넣어뒀는데, 실제 Gemini로 검증 데이터셋 117행(REVIEW_REQUIRED 정답 39건 포함)을 돌려보니
정답이 REVIEW_REQUIRED인 39건 중 **0~1건만 맞혔다** — 항상 MATCHED나 NOT_MATCHED로 확신에
차서 답했다. 실제 사례("우리 아이 첫 영양제로 좋아요", "차세대 기술로 만든 제품")를 보면
라벨링 자체는 합리적이라, 모델이 지시를 형식적으로만 읽고 실제로는 안 따르는 게 원인이었다.

시도한 것 중 안 먹힌 것들:
- 판단 기준을 3개로 구체화(문장 해석이 갈릴 수 있음/문장 밖 정황 필요/근거문서 있어도 확정 아님)
  → 0/39 → 5/39로 소폭 개선에 그침.
- few-shot 대비 예시 추가 → 5/39 그대로, 전체 정확도는 오히려 하락(70.1%→67.5%) → 되돌림.
- "문장에서 판단 근거를 인용하고, 없으면 '없음'이라고 쓰라"는 필드 추가 → **39건 전부 문장
  전체를 그대로 인용해버려 "없음" 응답이 0건** — 강제력이 전혀 없었다. 전체 정확도도 하락
  (66.7%) → 되돌림.

먹힌 것: **"needsOutsideContext"(문장 밖 정보가 필요한가)를 true/false로 먼저 답하게 하고,
true면 status를 무조건 REVIEW_REQUIRED로 고정**하는 구조적 게이트로 바꾸자 REVIEW_REQUIRED가
5/39→22/39(56%)로 개선됐다(전체 정확도 70.1%→75.2%). true로 답한 34건은 100% 전부
REVIEW_REQUIRED로 이어져 지시를 완벽히 따랐다 — "판단이 애매하면"이라는 애매한 지시보다
"문장 밖 정보가 필요한가"라는 구체적 예/아니오 질문으로 바꾼 게 핵심이었다. 교훈: LLM에게
"애매하면 이렇게 답해라" 식 조건부 지시는 잘 안 먹히고, 먼저 이분법적 판단(게이트)을 시키고
그 결과로 최종 답을 강제로 고정하는 2단계 구조가 훨씬 안정적이다.

### RAG grounding이 REVIEW_REQUIRED 인식을 방해함 — 두 프롬프트 버전에서 일관되게 관찰
판정 전에 근거 문서 원문을 프롬프트에 넣어주는 RAG grounding을 추가했는데, 두 프롬프트
버전(REVIEW_REQUIRED 지침 없는 최초 버전과 게이트 적용 최종 버전) 양쪽에서 공통적으로
**grounding을 켜면 REVIEW_REQUIRED 인식이 악화**됐다(1/39→0/39, 그리고 28/39→26/39).
게이트 버전에서는 전체 정확도도 grounding 없음(79.5%)이 있음(74.4%)보다 높게 나왔다(같은
설정을 다른 API 키로 재실행해도 약 1%p 차이만 났는데, 이 5.1%p 격차는 그보다 커서 우연이
아니라고 판단). 근거 문서 원문을 보여주면 모델이 "판단할 근거가 충분하다"고 여겨서 애매함을
덜 인정하게 되는 것으로 추정 — 팀과 논의 후 판정용 grounding은 끄기로 결정(`RagRuleGrounding
Provider`의 `@Component`를 제거해 나중에 자동으로 다시 켜지지 않게 함). 판정 **후** MATCHED
확정 Claim의 AI#2 설명문 인용 근거(`FindingAssembler.searchEvidence()`)는 완전히 별개
경로라 이 결정과 무관하게 그대로 유지된다.

### 배치 처리(evaluateBatch) — 네 가지 시도 다 실패, 결국 포기
Claim 1건에 여러 규칙이 적용될 때 개별 호출 대신 한 프롬프트에 묶어 JSON 배열로 받는
`evaluateBatch()`를 구현했는데, 같은 Claim에 같은 규칙 8개를 배치 1회 vs 개별 8회로 각각
돌려 결과가 일치하는지 실측하는 별도 테스트를 만들어 확인해보니 **일치율이 54~67%에 불과했다**
— 3분의 1가량이 다른 답. 불일치의 대부분(8건 중 7건)이 정확히 같은 패턴이었다: 배치=NOT_MATCHED,
개별=REVIEW_REQUIRED — 규칙 여러 개를 한 프롬프트에 몰아넣으니 그렇게 힘들게 만든
needsOutsideContext 게이트가 거의 무력화됐다.

네 가지 다른 방향으로 고쳐봤지만 전부 비슷하거나 더 나빴다:
1. 원본 배치(8개 통짜, 지침이 규칙 목록 뒤) — 16/24(66.7%)
2. 지침을 규칙 목록 앞으로 옮기고 규칙마다 리마인더 추가 — 13/24(54.2%), 오히려 악화
3. 청크 크기를 3개로 축소 — 16/24(66.7%), 무변화
4. 더 큰 모델(`gemini-3.5-flash`)로 교체 — 6/8(75.0%)로 개선 조짐은 있었으나, 이 모델의
   무료 티어 분당 제한이 5회뿐이라(`flash-lite`는 15회) **배치를 써도 개별호출보다 느려서**
   애초에 배치의 목적(속도 절감)에 안 맞았다.

세 번의 서로 다른 프롬프트/청크 크기 시도가 전부 54~67%에서 벗어나지 못한 것으로 보아, 이건
프롬프트 문구 문제가 아니라 "여러 규칙 판단을 한 호출에 동시에 시키는 방식 자체"가 이
모델에서 구조적으로 불안정하다는 뜻으로 판단했다. **배치를 포기**하고 `RuleEvaluator
.evaluateBatch()`의 기본 구현(규칙마다 `evaluate()` 개별 호출)을 그대로 쓰기로 결정 —
정확도(75.2%)를 지키는 대신 Claim당 호출 수(COMMON 12개 + 원료별 매핑분, 약 15~20회)는
그대로 감수한다. 상세페이지 1개 분석에 약 80~100회, 무료 티어 일일 500회 기준 하루 5~6
페이지가 한계라는 계산까지 나왔는데, 이 호출량 자체를 줄이는 건(예: 키워드 사전필터로 명백히
무관한 COMMON 규칙 스킵) 별도 과제로 남겨뒀다 — 다만 이 방식도 "정규식으로 안 돼서 AI에
맡긴" 애초의 이유와 같은 함정(키워드가 없어도 암시로 걸리는 케이스를 조용히 놓칠 위험)이
있어서 신중하게 설계해야 한다.

### 패턴1 프롬프트 수정 이후 16개 규칙 재검증 — 대부분 개선, E04/B03만 남음
"안정적으로 나쁨" 7개 + "여전히 애매함" 9개, 총 16개 규칙의 전체 claim(48건)을 패턴1 수정
프롬프트로 다시 돌렸다. E01_VESSEL·L03_EYE_DISEASE는 3/3 만점, 나머지 12개는 전부 2/3(REVIEW_
REQUIRED 정답 1건만 못 맞히는 동일 패턴)로 개선됐다 — 즉 패턴1 수정이 이 규칙들 대부분에 걸쳐
일관되게 통했다는 뜻이다. 유일하게 개선이 없던 두 규칙은 **E04_ALIAS(1/3)**와 **B03_OTHER_
ORAL(1/3)**이었는데, 둘 다 공통점이 있었다 — 검증 테스트 하네스가 `officialFunctions`(원료의
실제 공식 기능성 문구, 운영에서는 파이프라인 ②단계가 채워줌)를 항상 빈 리스트로 넘기고
있었다. 이 두 규칙은 원료의 실제 공식 명칭/기능성과 광고 문구를 대조해야 판단할 수 있는
규칙이라, 대조할 데이터 자체가 없는 상태로 테스트한 것이 원인일 수 있다고 의심했다.

### officialFunctions 채워서 재검증 — B03은 테스트 하네스 문제였고, E04는 진짜 모델 약점
의심을 확인하려고 실제와 비슷한 `officialFunctions` 데이터(원료의 진짜 공식 명칭+기능성 문구)를
채워서 E04(claim 3건)·B03(claim 1건)을 재평가했다.
- **B03_OTHER_ORAL**: Pattern1 재테스트에서 틀렸던 claim("외래진료 1위 치주질환 / 피가 난다 /
  고름 / 붓는 잇몸")이 실제 공식 기능성 문구("구강 내 항균작용에 도움을 줄 수 있음")를 채워주자
  정답(MATCHED)으로 정확히 나왔다. **테스트 하네스의 한계였을 뿐, 프롬프트나 모델의 문제가
  아니었다** — 운영 환경(파이프라인 ②단계가 실제 데이터를 채워줌)에서는 이 규칙이 정상 동작할
  것으로 판단, 파일럿 포함 가능.
- **E04_ALIAS**: 반대로 같은 조건(실제 오메가3 공식 기능성 문구를 채움)에서도 3건 중 2건이
  여전히 틀렸다("오메가3 500mg"을 NOT_MATCHED로, "오메가3(지방산 복합체) 500mg"도 NOT_MATCHED로
  오판) — officialFunctions 유무와 무관하게 계속 틀리는 것으로 보아 **데이터 공백이 아니라
  진짜 모델 약점**이라고 판단했다.

### 라벨을 모델 결과에 맞춰 바꾸려다 멈춘 사례 — 검증 방법론의 핵심 원칙
E04가 계속 틀리는 걸 보고, 처음엔 "혹시 원래 검증 데이터셋 라벨이 틀린 거 아닐까?"라는 생각으로
"오메가3 500mg"의 정답 라벨을 모델이 낸 NOT_MATCHED에 맞춰 고치려고 했다. 이때 "결과를 보고
라벨을 수정하면 애초에 그 테스트가 무슨 의미가 있냐"는 지적을 받았다 — 맞는 말이었다. 이전에
진행했던 5건의 정당한 라벨 수정(L03_EYE_DISEASE 등)과 이번 시도의 결정적 차이는 **독립적인
근거의 유무**였다: 그 5건은 모델의 판단 근거를 규칙의 `candidateExamples`(팀이 미리 정리해둔
판례)와 대조해서 확인한 것이었지만, 이번엔 그냥 "모델이 이렇게 말하니까 라벨이 틀렸겠지"라는
추측뿐이었다.

그래서 실제 근거 문서(`reference_sources_v0.1_embeddings.json`에 저장된 KHFF NOTICE-01
원문)를 직접 읽어서 확인했다. 원문에 "EPA및DHA함유 유지" 문구를 광고하려면 식약처 고시
원료명칭을 쓰거나, 광고물 안에서 올바른 기능성 원료명(별칭)을 명확히 병기해야 "오메가3"라는
표현을 나머지 위치에 쓸 수 있다고 명시돼 있었다 — 즉 "오메가3 500mg"처럼 별칭만 단독으로 쓰고
정식 명칭 병기가 전혀 없는 문구는 **원래 라벨(MATCHED, 위반)이 맞고 모델이 틀린 것**이었다.
라벨을 건드리지 않길 잘한 사례로, 이후 원칙으로 삼는다: **검증 데이터셋 라벨은 모델이
반대되는 답을 낸다는 이유만으로 절대 수정하지 않는다 — 규칙의 판례/실제 근거 문서 등 라벨
자체와 독립된 근거로 확인됐을 때만 수정한다.**

### 결론 — 28개 규칙으로 1차 파일럿 확정, 나머지는 2단계 백로그
Common 3개 + Literal 9개 + AI 16개(재현성 검증까지 마친 9개 + 패턴1 수정 후 2/3 이상으로
안정화된 7개: C03/C04/C13/C14/C21/G05/M04/B01/S02/C22 중 재현성 3회 검증까지 마친 것과
합산), 총 28개를 `RuleJudgeProperties.enabledRuleCodes`에 등록해 1차 파일럿으로 확정했다.
남은 규칙들(E04_ALIAS, C13_TESTIMONIAL의 난이도 역전 의심 등)은 "2단계 백로그"로 남기고 이번
파일럿에는 포함하지 않았다 — 오늘 확인한 것처럼 애매한 부분을 무리하게 서두르기보다, 규칙별로
근거를 갖고 하나씩 검증하는 게 검증 데이터셋의 신뢰성을 지키는 길이라고 판단했기 때문이다.

### Gemini 무료 티어 — 모델마다, 그리고 호출 종류마다 제한이 다 다름
이번에 겪으며 확인된 것만 정리:
- `generate_content`(`gemini-3.5-flash-lite`): 분당 15회
- `generate_content`(`gemini-3.5-flash`): 분당 **5회** — 모델을 한 단계 올렸다고 방심하면
  오히려 병목이 더 심해질 수 있다.
- `embed_content`(`gemini-embedding-001`류): 분당 100회 **+ 일일 1,000회**. 분당 제한만
  신경 쓰다가 일일 제한에 걸려서 그날은 재시도로도 복구가 안 됐다(재시도 백오프는 분당
  제한에만 효과가 있고 일일 한도 소진에는 무의미).
- `batchEmbedContents`: 배치 자체에 "최대 100건" 하드 제한이 있고(초과 시 400 에러),
  더 중요하게는 **배치 안 항목 수만큼 분당 쿼터를 그대로 차감하는 것으로 보임** — 90건을
  한 배치로 보내도 429가 났다. `RagRetrievalService.searchBatch()`가 배치 실패 시 개별
  호출로 자동 폴백하는데, 이 폴백 경로엔 호출 간 지연이 없어서 대량 배치가 실패하면 곧바로
  분당 한도를 넘기며 연쇄 실패한다 — 애초에 배치 크기를 100보다 훨씬 낮게(40 이하) 잡아서
  폴백 자체를 안 타게 하는 게 안전하다.

## OCR 엔진 대안 검토 (Gemini Vision 비용 절감)

멘토링에서 "OCR 등 일부 전처리를 Extension/브라우저 쪽에서 처리할 수 있는지" 의견이 나와서,
Gemini Vision OCR을 더 싸거나 무료인 엔진으로 대체할 수 있는지 실제 상품 이미지로 검증했다.
아래는 순서대로 시도한 기록이다.

### Tesseract — 원료표에서 완전히 못 쓸 수준으로 실패, 원인은 "작은 글씨"가 아니었음
실제 상품 이미지 5장(마케팅 배너 2장, 원료표·영양정보가 포함된 상세페이지 2장, 제품 패키지
사진 1장)으로 Tesseract(`kor+eng`)를 Gemini와 나란히 돌렸다. 큰 마케팅 문구는 얼추 읽었지만,
가장 중요한 원료표·영양정보 표가 완전히 못 쓸 수준으로 깨졌다("우으따르마 매매으세아다아"처럼
의미 없는 문자열). 스타일화된 배너 이미지도 텍스트 대부분을 놓쳤다(한 줄만 인식하고 나머지
20줄 이상을 통째로 누락).

원인을 파다가 중요한 사실을 발견했다: 원료표 영역만 잘라서(crop) 다시 돌리니 **같은 내용이
거의 Gemini급으로 정확하게 나왔다.** 즉 Tesseract의 진짜 문제는 "작은 글씨를 못 읽는 것"이
아니라 "사진과 텍스트가 뒤섞인 긴 페이지를 통째로 넣으면 페이지 레이아웃 분석 자체가 헝클어지는
것"이었다. 업스케일링+PSM 6 조합 자체의 개선 효과는 미미했고, "마케팅 사진 영역과 텍스트 표
영역을 분리해서 처리하는 것"이 훨씬 크게 작용했다.

### EasyOCR — 한 약점이 다른 약점으로 바뀔 뿐, 개선이 아니었음
PyTorch 기반 딥러닝 OCR인 EasyOCR도 같은 5장으로 테스트했다. 스타일화된 배너 텍스트는
Tesseract보다 확실히 나았지만(최소한 줄 자체는 놓치지 않음), 가장 길고 복잡한 이미지(세로
25,000px 상세페이지)에서는 원료표 섹션을 통째로 누락해서 오히려 Tesseract보다 나빴다. 같은
크롭 전처리를 적용하면 Tesseract와 비슷한 수준까지 올라오지만, 속도가 Tesseract보다 5~10배
느려서(크롭 기준 이미지당 6~7초) 채택할 이유가 없었다.

(참고) 설치 과정에서 EasyOCR의 모델 다운로드 진행률 표시줄이 Windows 콘솔 인코딩(cp949)과
충돌해서 `UnicodeEncodeError`로 크래시하는 문제가 있었다 — `PYTHONIOENCODING=utf-8`과
`python -X utf8`로 강제해서 해결. OCR 로직 자체의 문제는 아니었다.

### PaddleOCR — 가장 유망한 후보, 다만 검증 초기 단계
Baidu의 딥러닝 OCR. **원료표 핵심 수치(진세노사이드 함량, 나트륨 mg, %비율 등)를 Gemini와
완전히 동일하게 뽑아냈다** — Tesseract/EasyOCR에서는 못 봤던 수준의 정확도. 다만 넘어야 할
장애물이 있었다:
- PaddlePaddle이 이 머신의 Python 3.14를 아직 지원하지 않아, `py -3.12`로 별도 가상환경을
  만들어야 했다.
- 첫 실행에서 PaddlePaddle 내부 추론엔진(oneDNN) 버그로 크래시했다
  (`NotImplementedError: ConvertPirAttribute2RuntimeAttribute not support ...` at
  `onednn_instruction.cc`) — `enable_mkldnn=False`로 우회.
- 기본 설정(무거운 `PP-OCRv5_server_det` 검출 모델) 기준 5장에 121초로 매우 느렸다. 가벼운
  검출 모델(`PP-OCRv5_mobile_det`)로 교체하니 63초로 개선됐고(약 2배), 정확도는 떨어지지
  않았다(오히려 일부 필드는 더 잘 잡음). 단, `PaddleOCR(...)`에 `text_detection_model_name`을
  직접 지정하면 `lang` 파라미터가 무시되면서 인식(rec) 모델까지 의도치 않게 다른 것으로
  바뀌어버리는 함정이 있었다 — `text_recognition_model_name`도 같이 명시해서 고정해야 한다.
- 그래도 Gemini(정상 크기 이미지 3장 기준 2.3초) 대비 수 배 느리고, **Java 바인딩이 없어**
  Backend(Spring Boot)와 별개로 Python 마이크로서비스를 상시 운영해야 하는 부담이 생긴다.

### 103장 전체 확대 검증 — PaddleOCR도 결국 기각
5장 표본에서 PaddleOCR이 유망해 보여서, 19개 상품(실제 이미지 103장) 전체로 Gemini와 정량
비교했다. 결과가 5장 때보다 훨씬 신중해졌다:
- 텍스트 유사도(문자열 순서 기반)가 리뷰사진 제외 기준 평균 0.726 — 나쁘지 않지만 완벽과는 거리가
  있었다. 단어집합 기반(Jaccard)으로는 0.535로 더 낮았는데, 두 지표가 이렇게 갈리는 이유 자체가
  "반복되는 디자인 배지 텍스트를 다른 순서로 읽는" 문제였다(실제로는 같은 내용, 순서만 다름).
- 실제 원문 대조(정관장 홍삼진고 사례)에서 원료표 수치는 대체로 맞았지만, "1일 섭취량 1포"를
  "2포"로 오인식하거나 원료 등급 설명 앞부분이 통째로 누락되는 등 **작지만 진짜인 오류**가 나왔다.
- 더 크게 걱정되는 지점은 원료표가 아니라 **본문 마케팅 카피(Claim이 실제로 있는 곳)를 상당 부분
  놓치는 문제**였다 — 임상시험 그래프 설명 등 긴 페이지의 절반 가까운 분량이 빠지는 사례가 있었음.
- GIF 파일 완전 미지원(`Not supported input file type!`), 103장 처리에 613초(Gemini는 140초) —
  약 4.4배 느림.

**최종 결론**: Gemini Vision OCR을 유지하기로 했다. Tesseract·EasyOCR·PaddleOCR 셋 다 무료
대안으로는 정확도(특히 Claim이 담긴 본문 텍스트 누락)와 속도 양쪽에서 Gemini를 대체할 근거가
부족했다.

### (조사만 함) Chrome 내장 AI — Gemini Nano Prompt API
멘토님이 "OCR을 사용자의 로컬 자원으로 돌리는 방향"도 고민해보라고 해서, Tesseract.js 같은
전통 OCR 라이브러리 말고 **Chrome이 제공하는 온디바이스 LLM(Gemini Nano)을 브라우저에서 직접
호출하는 방법**이 있는지 조사했다(코드는 안 건드리고 조사만).

- Chrome의 `Prompt API`(`window.ai`/`LanguageModel`)가 이미지 입력을 지원한다. `HTMLImageElement`,
  `Blob`, `ImageData` 등을 그대로 넣을 수 있어서, 원리상 Extension이 이미지를 캡처해 Gemini
  Nano에 직접 넘기고 서버 호출 없이 텍스트를 뽑을 수 있다.
- 기기 요구사항이 꽤 높다: 저장공간 22GB 이상, GPU면 VRAM 4GB 초과 또는 CPU면 16GB RAM+4코어
  이상. 이 조건 미달 사용자는 기능 자체가 없어서 Gemini API 서버 폴백이 항상 같이 필요하다.
  (참고: 개발 기기 기준으로는 Chrome 152, RAM 31.5GB, 여유디스크 799GB, GPU VRAM 6.1GB로 전부
  충족 — 다만 이건 개발 기기 하나일 뿐, 실제 사용자 기기 커버리지는 별도 확인 필요.)
- 이미지(멀티모달) 입력은 아직 완전한 stable이 아니라 **Origin Trial** 단계다. 사용자가 API
  키나 비용을 내는 구조는 아니고, 개발자(우리)가 Chrome for Developers에서 무료로 발급받는
  Origin Trial 토큰을 Extension manifest/HTML에 넣어야 켜지는 방식이다. 토큰에 유효기간이
  있고, 정식 출시 전까지 API 형태가 바뀔 수 있다는 리스크가 있다.
- Gemini Nano의 실제 원료표·Claim 텍스트 추출 정확도는 검증된 적이 없다(공식 문서도 OCR을
  명시적으로 언급하지 않고 "이미지 캡션 생성" 정도로만 소개함) — Tesseract/EasyOCR/PaddleOCR
  때와 같은 실측 비교가 필요하지만, 아직 진행 전이다.

**채택하지 않은 이유**: 지금 시점에서는 이 방향을 실제로 채택하지 않기로 했다. 가장 큰 이유는
정확도 미검증이 아니라, **아직 정식(stable) 기능이 아니라 Origin Trial(실험) 단계**라는 점이다 —
토큰 유효기간이 있고 정식 출시 전까지 API 자체가 바뀔 수 있어서, 지금 프로덕션에 의존하기엔
기반이 불안정하다고 판단했다.
