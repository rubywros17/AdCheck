## AI 파이프라인 (Claim/원료표시 추출)

### 원료 표시 추출 — 후보 2개 이상이면 null 반환
LLM한테 "원료표에 해당하는 문자열을 새로 만들어서 반환해"라고 시켰더니, 실제 이미지로 테스트할
때 후보(원료표)가 1개면 정상 작동하고 2개 이상이면 아예 `null`을 반환하는 비결정적 문제가
있었다. 반환 타입을 `String` → `List<String>`으로 바꾸고 "하나만 고르지 말고 전부 배열로
반환"하도록 프롬프트를 바꿔서 해결.

### 원료 표시 추출 — 원문 개행 보존으로 콤마 분리가 깨짐
"원문 그대로 옮기라"는 지시를 LLM이 충실히 따르면서, 이미지 폭 때문에 여러 줄로 잘린 OCR
텍스트의 개행 문자까지 그대로 보존한 채 반환했다. 그 결과 `IngredientSplitter`의 콤마 분리
로직이 깨져서 정상 매칭이 안 됐다. LLM한테 문자열을 새로 "생성"시키는 대신, 본문+OCR 텍스트를
줄 단위로 번호 매겨 주고 "원료표에 해당하는 줄 번호만 골라줘"라고 시키는 방식(줄 선택)으로
바꿔서 해결 — 실제 문자열 조립은 코드가 하므로 원문 왜곡 문제가 원천적으로 안 생긴다.

### 광고 문구 속 수치를 원료로 오인식
"성분명+함량 단위가 붙어있으면 다 후보로"라고 시켰더니, "진세노사이드 Rg1+Rb1+Rg3 합
16mg/g"처럼 실제로는 효능 주장·비교용 수치인 걸 원료표로 잘못 뽑는 경우가 있었다. 재구성한
후보 문자열을 곧바로 `IngredientMatchingService`에 넣어보고, 그 안에 하나도 매칭되는 원료가
없으면(전부 UNMATCHED) 후보 자체를 버리도록 해서 해결 — 이미 검증된 매칭엔진을 품질 필터로
재활용.

### Gemini 호출 무한 대기 (타임아웃 미설정)
`GeminiClient`/`GeminiOcrService`에 커넥션/응답 타임아웃이 전혀 설정돼 있지 않아서, 네트워크가
느려지면 스레드가 응답을 무한정 기다리는 버그가 있었다. 단위 테스트로는 절대 안 잡히고, 실제
E2E 테스트 중 앱이 멈춘 걸 보고 `jstack`으로 스레드 덤프를 떠서 `JdkClientHttpRequest
.executeInternal`에 36초 넘게 멈춰있는 스레드를 발견해서야 알았다. `SimpleClientHttp
RequestFactory`에 connect 10초/read 60초 타임아웃을 명시해서 해결.

### Gemini 무료 티어 일일 할당량(500회) 초과
105장 이미지 검증 배치를 돌리다 하루 요청 한도(`GenerateRequestsPerDayPerProjectPerModel-
FreeTier`, 500회)를 다 써서 중간에 API 키를 바꿔서 이어서 처리해야 했다. 근본적으로는 이미지별
개별 호출(1장=OCR 1회+Claim 1회) 구조가 낭비였던 것이라, 이후 OCR을 상품 단위로 배치 호출하고
Claim/원료표시 추출을 프롬프트 하나로 합쳐서 상품당 호출 수를 4회→2회로 줄였다.

## 원료 매칭 알고리즘

### Python→Java 포팅 시 반올림 방식 차이
Python `round()`는 은행반올림(half-even)인데 Java `Math.round()`는 반올림(half-up)이라,
정확히 중간값(0.625 등)인 유사도 점수에서 결과가 갈리는 버그가 있었다. `BigDecimal
.HALF_EVEN`으로 고쳐서 Python 원본과 100% 동일한 결과가 나오도록 맞췄다(288개 케이스 파리티
테스트로 확인).

### v0.2 재작성 시 괄호 제거로 인한 오매칭
Data Contract v0.2 기준으로 원료 매칭을 다시 짜면서, 정규화 함수가 문자열 안의 괄호 내용까지
통째로 지우고 비교하도록 짰었다. 그랬더니 "인삼분말(가루, 과립)(인삼근 70%, 인삼미삼 30%)"
같은 설명형 문자열이 괄호를 지우면 "인삼분말"이 되어, 실제로는 UNMATCHED여야 하는데 동의어사전의
"인삼분말"과 우연히 일치해서 잘못 MATCHED로 판정됐다. 팀원이 준 실제 계산 결과 256건 샘플로
검증하다가 발견 — 괄호는 그대로 보존하고 공백(개행 포함)만 제거하도록 정규화 방식을 바꿔서
해결, 240/256(93.75%) 파리티 확보.

### 팀원 데이터 자체의 시점 불일치 (알고리즘 버그 아님)
파리티 검증 중 `RAW_RECOGNITION_NO`/`UNMATCHED` 조합 16건에서만 계속 불일치가 났다. 원인을
추적해보니 `ingredient_synonyms_v0.2.csv`엔 이미 정확일치 동의어로 등록된 문자열이, 팀원이
사전 계산해준 `product_ingredient_matches_v0.2.csv`엔 UNMATCHED로 남아있는 경우였다 —
동의어사전 쪽이 더 최신이고 계산 결과 파일이 이전 버전 기준으로 만들어진 것으로 보임. 우리
알고리즘 문제가 아니라고 판단해서 이 조합만 검증 대상에서 제외하고, 팀원에게 확인 요청.

## Analysis API / 파이프라인 실행

### `@Async` + `@Transactional` 조합으로 트랜잭션 가시성 버그
분석 요청을 비동기로 처리하도록 바꾸면서, `submit()` 메서드에 `@Transactional`을 걸어놨더니
비동기 스레드가 시작될 때 아직 원본 트랜잭션이 커밋되기 전이라(READ_COMMITTED 격리수준) 방금
저장한 행을 못 찾는 문제가 있었다. DB를 계속 폴링해도 상태가 PENDING에서 안 바뀌는 걸 보고
발견 — `submit()`에서 `@Transactional`을 빼서, 저장이 먼저 커밋된 뒤에 비동기 작업이 시작되게
해서 해결.

### Hibernate `ddl-auto:update`가 고아 컬럼/테이블을 안 지움
엔티티에서 필드를 삭제해도 Hibernate가 실제 DB 컬럼은 그대로 둔다. `detail_text` 등 안 쓰는
컬럼에 남아있던 NOT NULL 제약 때문에 새 저장 로직이 `DataIntegrityViolationException`으로
실패했다. 직접 psycopg2로 접속해서 `ALTER TABLE ... DROP COLUMN`으로 정리해서 해결(로컬
개발용 DB, 테스트 데이터만 있어서 안전하게 진행).

## DB / Flyway 마이그레이션

### Spring Boot 4.x는 `spring-boot-flyway` 모듈이 따로 필요
`org.flywaydb:flyway-core`만 추가하고 실행했더니 Flyway가 아예 동작을 안 했다(로그에 Flyway
관련 언급이 한 줄도 없이 곧바로 Hibernate 스키마 검증에서 "missing table" 에러가 남). Spring
Boot 4.x부터 자동설정이 기술별로 분리된 모듈 구조라(`spring-boot-hibernate`,
`spring-boot-jdbc`처럼), Flyway 자동설정도 `org.springframework.boot:spring-boot-flyway`를
따로 추가해야 활성화됐다.

### `IngredientMatchingService`에 생성자 2개 두니 Spring 빈 생성 실패
DB 조회용 생성자(Repository 4개 받음)와 테스트용 생성자(엔티티 리스트 직접 받음)를 같이
두었더니 "No default constructor found" 에러가 났다. 생성자가 여러 개면 Spring이 어느 걸
autowiring에 쓸지 못 정하는 문제라, DB 조회용 생성자에 `@Autowired`를 명시해서 해결.

### Jackson CSV — record가 CSV의 일부 컬럼만 모델링하면 파싱 실패
CSV에 컬럼이 더 있는데 record는 필요한 몇 개만 필드로 갖고 있으면
`UnrecognizedPropertyException`이 난다(예: `functional_ingredients_v0.2.csv`의
`recognizedAt`/`companyName` 등). `@JsonIgnoreProperties(ignoreUnknown = true)`를 빠뜨릴
때마다 반복해서 겪은 실수 — record가 CSV 전체 컬럼을 안 담을 거면 항상 이 애노테이션을 붙여야
한다.

### `ad_cases_v0.1.csv`의 `ruleCodes` 필드에 부가설명이 섞여 들어옴
콤마로 구분된 규칙 코드 목록인데, "DISC-*" 계열 사례 18건 중 14건은 마지막 코드 뒤에
"; 부가설명문구"가 그대로 붙어있었다(예: `"C01_DISEASE_PREVENTION; 질병정보 구분 필요"`).
콤마로 나눈 뒤 각 토큰을 다시 세미콜론으로 나눠 앞부분만 규칙 코드로 취급하도록 파싱 로직을
추가해서 해결.

### JPA 엔티티의 `protected` 무인자 생성자를 테스트에서 직접 호출 불가
테스트 픽스처를 만들면서 다른 패키지에서 `new IngredientMasterEntity()`를 직접 호출했더니
컴파일 에러(`protected` 접근 제한). `BeanUtils.instantiateClass(Class)`로 접근 제한을 우회해서
인스턴스를 만들고, 필드는 `ReflectionTestUtils.setField()`로 채우는 방식으로 해결.

## Rule Judge (AI#3 — AiRuleEvaluator)

### REVIEW_REQUIRED를 사실상 못 냄 — 지시만 있고 실효가 없었음
프롬프트에 "판단이 애매하거나 근거 자료가 부족하면 REVIEW_REQUIRED로 답하세요"라는 지시를
넣어뒀는데, 실제 Gemini로 검증 데이터셋 117행(REVIEW_REQUIRED 정답 39건 포함)을 돌려보니
정답이 REVIEW_REQUIRED인 39건 중 **0~1건만 맞혔다** — 항상 MATCHED나 NOT_MATCHED로 확신에
차서 답했다. 실제 사례("우리 아이 첫 영양제로 좋아요", "차세대 기술로 만든 제품")를 보면
라벨링 자체는 합리적이라, 모델이 지시를 형식적으로만 읽고 실제로는 안 따르는 게 원인이었다.

시도한 것 중 안 먹힌 것들:
- 판단 기준을 3개로 구체화(문장 해석이 갈릴 수 있음/문장 밖 정황 필요/근거문서 있어도 확정 아님)
  → 0/39 → 5/39로 소폭 개선에 그침.
- few-shot 대비 예시 추가 → 5/39 그대로, 전체 정확도는 오히려 하락(70.1%→67.5%) → 되돌림.
- "문장에서 판단 근거를 인용하고, 없으면 '없음'이라고 쓰라"는 필드 추가 → **39건 전부 문장
  전체를 그대로 인용해버려 "없음" 응답이 0건** — 강제력이 전혀 없었다. 전체 정확도도 하락
  (66.7%) → 되돌림.

먹힌 것: **"needsOutsideContext"(문장 밖 정보가 필요한가)를 true/false로 먼저 답하게 하고,
true면 status를 무조건 REVIEW_REQUIRED로 고정**하는 구조적 게이트로 바꾸자 REVIEW_REQUIRED가
5/39→22/39(56%)로 개선됐다(전체 정확도 70.1%→75.2%). true로 답한 34건은 100% 전부
REVIEW_REQUIRED로 이어져 지시를 완벽히 따랐다 — "판단이 애매하면"이라는 애매한 지시보다
"문장 밖 정보가 필요한가"라는 구체적 예/아니오 질문으로 바꾼 게 핵심이었다. 교훈: LLM에게
"애매하면 이렇게 답해라" 식 조건부 지시는 잘 안 먹히고, 먼저 이분법적 판단(게이트)을 시키고
그 결과로 최종 답을 강제로 고정하는 2단계 구조가 훨씬 안정적이다.

### RAG grounding이 REVIEW_REQUIRED 인식을 방해함 — 두 프롬프트 버전에서 일관되게 관찰
판정 전에 근거 문서 원문을 프롬프트에 넣어주는 RAG grounding을 추가했는데, 두 프롬프트
버전(REVIEW_REQUIRED 지침 없는 최초 버전과 게이트 적용 최종 버전) 양쪽에서 공통적으로
**grounding을 켜면 REVIEW_REQUIRED 인식이 악화**됐다(1/39→0/39, 그리고 28/39→26/39).
게이트 버전에서는 전체 정확도도 grounding 없음(79.5%)이 있음(74.4%)보다 높게 나왔다(같은
설정을 다른 API 키로 재실행해도 약 1%p 차이만 났는데, 이 5.1%p 격차는 그보다 커서 우연이
아니라고 판단). 근거 문서 원문을 보여주면 모델이 "판단할 근거가 충분하다"고 여겨서 애매함을
덜 인정하게 되는 것으로 추정 — 팀과 논의 후 판정용 grounding은 끄기로 결정(`RagRuleGrounding
Provider`의 `@Component`를 제거해 나중에 자동으로 다시 켜지지 않게 함). 판정 **후** MATCHED
확정 Claim의 AI#2 설명문 인용 근거(`FindingAssembler.searchEvidence()`)는 완전히 별개
경로라 이 결정과 무관하게 그대로 유지된다.

### 배치 처리(evaluateBatch) — 네 가지 시도 다 실패, 결국 포기
Claim 1건에 여러 규칙이 적용될 때 개별 호출 대신 한 프롬프트에 묶어 JSON 배열로 받는
`evaluateBatch()`를 구현했는데, 같은 Claim에 같은 규칙 8개를 배치 1회 vs 개별 8회로 각각
돌려 결과가 일치하는지 실측하는 별도 테스트를 만들어 확인해보니 **일치율이 54~67%에 불과했다**
— 3분의 1가량이 다른 답. 불일치의 대부분(8건 중 7건)이 정확히 같은 패턴이었다: 배치=NOT_MATCHED,
개별=REVIEW_REQUIRED — 규칙 여러 개를 한 프롬프트에 몰아넣으니 그렇게 힘들게 만든
needsOutsideContext 게이트가 거의 무력화됐다.

네 가지 다른 방향으로 고쳐봤지만 전부 비슷하거나 더 나빴다:
1. 원본 배치(8개 통짜, 지침이 규칙 목록 뒤) — 16/24(66.7%)
2. 지침을 규칙 목록 앞으로 옮기고 규칙마다 리마인더 추가 — 13/24(54.2%), 오히려 악화
3. 청크 크기를 3개로 축소 — 16/24(66.7%), 무변화
4. 더 큰 모델(`gemini-3.5-flash`)로 교체 — 6/8(75.0%)로 개선 조짐은 있었으나, 이 모델의
   무료 티어 분당 제한이 5회뿐이라(`flash-lite`는 15회) **배치를 써도 개별호출보다 느려서**
   애초에 배치의 목적(속도 절감)에 안 맞았다.

세 번의 서로 다른 프롬프트/청크 크기 시도가 전부 54~67%에서 벗어나지 못한 것으로 보아, 이건
프롬프트 문구 문제가 아니라 "여러 규칙 판단을 한 호출에 동시에 시키는 방식 자체"가 이
모델에서 구조적으로 불안정하다는 뜻으로 판단했다. **배치를 포기**하고 `RuleEvaluator
.evaluateBatch()`의 기본 구현(규칙마다 `evaluate()` 개별 호출)을 그대로 쓰기로 결정 —
정확도(75.2%)를 지키는 대신 Claim당 호출 수(COMMON 12개 + 원료별 매핑분, 약 15~20회)는
그대로 감수한다. 상세페이지 1개 분석에 약 80~100회, 무료 티어 일일 500회 기준 하루 5~6
페이지가 한계라는 계산까지 나왔는데, 이 호출량 자체를 줄이는 건(예: 키워드 사전필터로 명백히
무관한 COMMON 규칙 스킵) 별도 과제로 남겨뒀다 — 다만 이 방식도 "정규식으로 안 돼서 AI에
맡긴" 애초의 이유와 같은 함정(키워드가 없어도 암시로 걸리는 케이스를 조용히 놓칠 위험)이
있어서 신중하게 설계해야 한다.

### 패턴1 프롬프트 수정 이후 16개 규칙 재검증 — 대부분 개선, E04/B03만 남음
"안정적으로 나쁨" 7개 + "여전히 애매함" 9개, 총 16개 규칙의 전체 claim(48건)을 패턴1 수정
프롬프트로 다시 돌렸다. E01_VESSEL·L03_EYE_DISEASE는 3/3 만점, 나머지 12개는 전부 2/3(REVIEW_
REQUIRED 정답 1건만 못 맞히는 동일 패턴)로 개선됐다 — 즉 패턴1 수정이 이 규칙들 대부분에 걸쳐
일관되게 통했다는 뜻이다. 유일하게 개선이 없던 두 규칙은 **E04_ALIAS(1/3)**와 **B03_OTHER_
ORAL(1/3)**이었는데, 둘 다 공통점이 있었다 — 검증 테스트 하네스가 `officialFunctions`(원료의
실제 공식 기능성 문구, 운영에서는 파이프라인 ②단계가 채워줌)를 항상 빈 리스트로 넘기고
있었다. 이 두 규칙은 원료의 실제 공식 명칭/기능성과 광고 문구를 대조해야 판단할 수 있는
규칙이라, 대조할 데이터 자체가 없는 상태로 테스트한 것이 원인일 수 있다고 의심했다.

### officialFunctions 채워서 재검증 — B03은 테스트 하네스 문제였고, E04는 진짜 모델 약점
의심을 확인하려고 실제와 비슷한 `officialFunctions` 데이터(원료의 진짜 공식 명칭+기능성 문구)를
채워서 E04(claim 3건)·B03(claim 1건)을 재평가했다.
- **B03_OTHER_ORAL**: Pattern1 재테스트에서 틀렸던 claim("외래진료 1위 치주질환 / 피가 난다 /
  고름 / 붓는 잇몸")이 실제 공식 기능성 문구("구강 내 항균작용에 도움을 줄 수 있음")를 채워주자
  정답(MATCHED)으로 정확히 나왔다. **테스트 하네스의 한계였을 뿐, 프롬프트나 모델의 문제가
  아니었다** — 운영 환경(파이프라인 ②단계가 실제 데이터를 채워줌)에서는 이 규칙이 정상 동작할
  것으로 판단, 파일럿 포함 가능.
- **E04_ALIAS**: 반대로 같은 조건(실제 오메가3 공식 기능성 문구를 채움)에서도 3건 중 2건이
  여전히 틀렸다("오메가3 500mg"을 NOT_MATCHED로, "오메가3(지방산 복합체) 500mg"도 NOT_MATCHED로
  오판) — officialFunctions 유무와 무관하게 계속 틀리는 것으로 보아 **데이터 공백이 아니라
  진짜 모델 약점**이라고 판단했다.

### 라벨을 모델 결과에 맞춰 바꾸려다 멈춘 사례 — 검증 방법론의 핵심 원칙
E04가 계속 틀리는 걸 보고, 처음엔 "혹시 원래 검증 데이터셋 라벨이 틀린 거 아닐까?"라는 생각으로
"오메가3 500mg"의 정답 라벨을 모델이 낸 NOT_MATCHED에 맞춰 고치려고 했다. 이때 "결과를 보고
라벨을 수정하면 애초에 그 테스트가 무슨 의미가 있냐"는 지적을 받았다 — 맞는 말이었다. 이전에
진행했던 5건의 정당한 라벨 수정(L03_EYE_DISEASE 등)과 이번 시도의 결정적 차이는 **독립적인
근거의 유무**였다: 그 5건은 모델의 판단 근거를 규칙의 `candidateExamples`(팀이 미리 정리해둔
판례)와 대조해서 확인한 것이었지만, 이번엔 그냥 "모델이 이렇게 말하니까 라벨이 틀렸겠지"라는
추측뿐이었다.

그래서 실제 근거 문서(`reference_sources_v0.1_embeddings.json`에 저장된 KHFF NOTICE-01
원문)를 직접 읽어서 확인했다. 원문에 "EPA및DHA함유 유지" 문구를 광고하려면 식약처 고시
원료명칭을 쓰거나, 광고물 안에서 올바른 기능성 원료명(별칭)을 명확히 병기해야 "오메가3"라는
표현을 나머지 위치에 쓸 수 있다고 명시돼 있었다 — 즉 "오메가3 500mg"처럼 별칭만 단독으로 쓰고
정식 명칭 병기가 전혀 없는 문구는 **원래 라벨(MATCHED, 위반)이 맞고 모델이 틀린 것**이었다.
라벨을 건드리지 않길 잘한 사례로, 이후 원칙으로 삼는다: **검증 데이터셋 라벨은 모델이
반대되는 답을 낸다는 이유만으로 절대 수정하지 않는다 — 규칙의 판례/실제 근거 문서 등 라벨
자체와 독립된 근거로 확인됐을 때만 수정한다.**

패턴1 수정 후 1회 실행에서 2/3 이상으로 개선됐던 14개 규칙(E04/B03 제외)을 2회 더 재실행해(총 3회, 42건 재

### 패턴2 — "매번 똑같이 틀림" 7개 규칙 원인 분석과 두 번의 프롬프트 수정 시도, 6개는 실패
`rules_v0.1.csv`에서 이 7개 규칙(C14/C21/G05/M04/L01/M02/S02)의 실제 정의를 대조해보니 두 가지
패턴으로 좁혀졌다:
- **패턴 A(핵심 단어 등장 = 자동 위반으로 오판)**: G05("혈당 관리가 다이어트의 시작입니다"), L01("침침한
  눈"), S02("하루종일 앉아있는 당신의 허리를 위해") — 규칙의 핵심 키워드가 있다는 이유만으로 모델이
  확신에 차서 MATCHED를 냈지만, 실제로는 막연한 상황 묘사·소프트한 문구라 "강한 효능 확장/결합 주장"에는
  못 미친다.
- **패턴 B(규칙 자체의 예외 문구가 "별도 검토 필요"라는 신호인데 못 알아챔)**: C14의 `exceptions`
  필드에 "개발 직접 참여 사실... **별도 조건 검토**"라고 명시돼 있는데, 정확히 그 시나리오("이 제품
  개발에 참여한 의사가 추천합니다")를 모델이 그냥 MATCHED로 확정한다. M02도 "적격 인체시험 구획의
  지표는 **별도 심사**"인데 마찬가지.

이 두 패턴에 맞춰 프롬프트를 **두 번** 고쳤다:
1. 1차: [적용 조건] 설명 뒤에 "핵심 단어 등장 ≠ MATCHED" 일반 문구 추가 + REVIEW_REQUIRED 기준
   목록에 "(4) 예외 사항에 '별도 검토/심사' 문구가 있으면 REVIEW_REQUIRED 신호" 항목 추가.
   → 결과: **L01만 개선(2/3→3/3), 나머지 6개는 전혀 안 움직임.**
2. 2차: 일반 문구 대신 [적용 조건]/[예외 사항] 텍스트 **바로 옆에** 강제 지침을 붙임(예:
   `예외 사항: ...` 줄 바로 뒤에 "위 예외 사항에 '별도'가 있으면 스스로 판단하지 말고 반드시
   needsOutsideContext=true로 답하라"). → 결과: **똑같이 L01만 유지, 나머지 6개는 이번에도 전혀
   안 움직임**(S02는 오히려 과잉 MATCHED→과잉 NOT_MATCHED로 방향만 바뀜).

서로 다른 두 문구 버전이 6개 규칙에 대해 완전히 동일한 결과를 냈다는 것은, 이게 프롬프트 문구
문제가 아니라 **`gemini-3.5-flash-lite`가 "전문가 추천/인과관계 결합/신체부위 언급/지표 언급" 같은
패턴을 한 번 포착하면, 지침을 아무리 명시적으로·가까이 배치해도 재고하지 않는 더 근본적인 한계**로
보인다. 여기서 프롬프트 문구를 계속 바꿔가며 시도하는 건 수익 체감이 크다고 판단해 **중단**했다.
L01_VISION은 서로 다른 두 프롬프트 버전에서 연속 3/3이 나와(패턴1 프롬프트에서는 3회 내내 안정적으로
틀렸던 것과 대비) 등록했지만, 나머지 6개(C14/C21/G05/M04/M02/S02)는 백로그로 남기고 **다음에는
일반 지침이 아니라 규칙별 few-shot 예시나 더 강한 모델을 검토하는 방향으로 접근을 바꿔야 한다.**

### 버그 발견 — C03_MEDICINE_CONFUSION에서 모델 응답이 "해석 불가"로 반복 실패
"전국 약국 및 온라인몰에서 구매 가능합니다" claim이 2회 연속(3회 중 2회) 똑같은 문구
("AI 응답을 해석할 수 없어 확인이 필요합니다")로 실패했다. `AiRuleEvaluator.parseResponse()`를 보니
이건 모델의 판단 내용이 아니라 **status/reasonCode를 우리 enum으로 매핑하지 못했을 때의 하드코딩된 폴백
경로**였다(JSON 파싱 자체는 성공, `parseStatus()`/`parseReasonCode()`가 `null`을 반환하는 경우).
이 특정 claim에서 모델이 우리가 인식 못 하는 status/reasonCode 문자열을 반복해서 내놓고 있다는 뜻이라,
프롬프트 튜닝이 아니라 **원본 응답을 로깅해서 실제로 뭘 리턴하는지 확인해야 하는 별도 버그**로 분류하고
아직 원인 파악 전이다.

### 결론 — 32개 규칙으로 1차 파일럿 확정, 나머지는 2단계 백로그
Common 3개 + Literal 9개 + AI 20개(1차 9개 + 2차 7개 + 3차 3개: E01_VESSEL/L03_EYE_DISEASE/
C22_SUPERLATIVE + 4차 1개: L01_VISION), 총 32개를 `RuleJudgeProperties.enabledRuleCodes`에
등록해 1차 파일럿으로 확정했다. 남은 규칙들 — E04_ALIAS(진짜 모델 약점, 프롬프트 재설계 필요),
B03_OTHER_ORAL(officialFunctions 컨텍스트 필요, 테스트 하네스 개선 필요), "매번 똑같이 틀림"
6개(C14/C21/G05/M04/M02/S02, 두 번의 프롬프트 수정 시도 모두 실패 — 다음엔 규칙별 few-shot이나
더 강한 모델 검토 필요), 진짜 flaky 2개(C13/B01), 라벨 재검토 대상 C04, 응답 파싱 버그 의심 C03
— 은 "2단계 백로그"로 남기고 이번 파일럿에는 포함하지 않았다. 애매한 부분을 무리하게 서두르기보다,
규칙별로 근거를 갖고 하나씩 검증하는 게 검증 데이터셋의 신뢰성을 지키는 길이라고 판단했기 때문이다.

### 배치 흔들림의 원인을 `temperature`로 보고 0으로 고정 — 효과 없어서 되돌림
같은 프롬프트를 반복 실행하면 회차마다 판정이 갈리는 문제를 샘플링 탓으로 보고
`GenerationConfig`에 `temperature: 0`을 넣었다. 결과는 **재현성도 정확도도 개선 없음** —
C22_SUPERLATIVE 5회 실행에서 3회는 3/3, 2회는 1/3으로 여전히 갈렸고, 정확도는 11/15 →
9/15로 오히려 내려갔다(n=15라 노이즈 범위). 설정이 누락된 게 아닌지 요청 본문을 직접 찍어
확인했는데 `{"responseMimeType":"application/json","temperature":0.0}`으로 정상 전송되고
있었다. **Gemini는 temperature=0에서도 같은 입력에 다른 답을 낸다**(호스팅 모델의 배치
구성·라우팅 차이로 알려진 현상). 이득이 없어 되돌렸고, 그 결과 **flaky 규칙(E01/C13/B01 등)을
샘플링 설정으로 안정화하는 길은 닫혔다** — 남은 수단은 다수결(호출 3배, 무료 티어에선 불가)
정도라 당분간은 "반복 측정으로 평균을 본다"가 유일한 대응이다.

### 규칙당 1회 측정으로는 프롬프트 수정의 효과를 판단할 수 없다
C22 프롬프트를 고친 뒤 20개 규칙을 1회씩 재봤더니 합계가 51/60으로 **수정 전과 정확히 같았고**,
개별로는 4개가 ±1씩 움직였다(C22 0→1, L01 1→2, R01 3→2, E03 3→2). 이 숫자로는 "수정 효과",
"퇴행", "노이즈"를 구분할 수 없다 — 위 temperature 실험에서 확인했듯 같은 프롬프트도 회차마다
갈리기 때문이다. 3회 반복(규칙당 9건 표본)으로 다시 재고 나서야 R01의 퇴행이 실재한다는 것과
C22의 개선이 실재한다는 것이 갈렸다. 이후 프롬프트 측정은 `AiRuleEvaluatorBatchRegressionTest`
(allowlist에서 대상 규칙을 직접 읽고, `REGRESSION_RUNS`/`REGRESSION_RULES`로 반복 횟수와
대상을 조정)로 **최소 3회 반복**을 기본으로 한다.

### C22_SUPERLATIVE 0/9 → 8/9 — 규칙 텍스트가 프롬프트 뒤쪽 지침을 밀어내고 있었다
C22는 배치에서 3회 내내 3건 전부 틀렸다(0/9). 모델이 남긴 `reason`을 읽어보니 실패 모드가
둘로 나뉘었다.

- **케이스 1·2 → REVIEW_REQUIRED**: *"실증 자료의 진위를 외부에서 확인해야 하므로 문장만으로
  확정할 수 없다"*. C22의 `requiredEvidence`에 "실증자료"라는 단어가 박혀 있어서, 그 자료를
  지금 볼 수 없다는 사실을 "문장 밖 정보가 필요하다"는 신호로 읽은 것이다.
- **케이스 3 → NOT_MATCHED**: *"최고·최대 등 명시적 비교 표현이 아니므로 해당 없음"*.
  `candidateExamples`(유일/최고/최대/최초/고순도)에 없는 단어("남다른", "프리미엄")를 썼다는
  이유로 제외했다.

프롬프트 뒤쪽에 이미 두 경우를 막는 문구가 있었는데도 안 먹혔다 — **규칙 텍스트가 더 가깝고
구체적이라 밀린 것**으로 보고, 규칙 텍스트를 넣는 그 자리에서 한 번 더 막기로 했다.

### 두 경고를 다 넣었더니 C22는 올랐지만 R01이 9/9 → 6/9로 깎였다
`candidateExamples`와 `requiredEvidence` 양쪽에 경고를 넣은 결과, 합계는 85.0%로 그대로인데
구성만 바뀌었다(C22 0→5/9, L01 ↑, R01 9→6/9, E03 7→6/9). **잘 되던 규칙을 깎아 안 되던 규칙을
올린 셈**이라 좋은 거래가 아니었다. 프롬프트 수정본을 임시로 되돌려 R01·E03만 3회씩 재서
퇴행이 실재함을 확인했다(R01은 되돌린 상태에서 9/9).

R01의 실패 근거를 읽어보니 예상과 방향이 반대였다. "환절기에 든든한 면역력, 홍삼과 함께"가
정답 REVIEW_REQUIRED인데 **NOT_MATCHED로** 갔다(*"질병 예방·치료의 구체적 확장 주장으로 보기
어렵다"*). 수정 전에는 *"문장 자체만으로는 ... 명확히 확정하기 어려워 추가 맥락 확인이
필요하다"*로 정확히 판단하던 케이스다.

### 범인은 `candidateExamples` 경고였고, `requiredEvidence` 경고 하나면 충분했다
처음에는 `requiredEvidence` 경고의 "판단을 미루지 마세요"가 정당한 게이트 사용까지 억눌렀다고
보고 *"단, 문구 자체의 의미가 여러 갈래로 읽히는 경우는 별개"*를 덧붙였다. C22는 9/9가 되고
E03는 원복됐지만 **R01은 6/9 그대로**여서 진단이 틀렸음이 드러났다.

`candidateExamples` 경고만 제거하고 다시 재자 세 규칙이 모두 좋아졌다.

| 규칙 | 수정 전 | 양쪽 경고 | 좁힌 경고 | 근거 경고만 |
|---|---|---|---|---|
| C22_SUPERLATIVE | 0/9 | 5/9 | 9/9 | **9/9** |
| E03_GENERATION | 7/9 | 6/9 | 7/9 | **8/9** |
| R01_COLD | 9/9 | 6/9 | 6/9 | **8/9** |

`candidateExamples` 경고의 마지막 문장(*"판단 기준은 단어 목록이 아니라 [적용 조건]입니다"*)이
모델을 적용 조건 문구에 과하게 붙게 만들어, 조건에 문자 그대로 안 맞는 애매한 문구를
NOT_MATCHED로 밀어낸 것으로 보인다. **C22 3번 케이스도 근거 경고 하나만으로 풀렸으므로 애초에
필요 없는 경고였다** — 실패 근거 하나를 보고 두 가지 원인을 추정한 것이 과했다.

### 최종 — 경고 하나로 85.0% → 88.3%
`requiredEvidence` 경고 하나만 남긴 상태로 20개 규칙을 3회씩 재측정했다.

```
C22_SUPERLATIVE        5/9 → 8/9   ▲ +3        C01_DISEASE_PREVENTION  9/9 → 8/9   ▼ -1
R01_COLD               6/9 → 8/9   ▲ +2        O02_ENERGY_EXPANSION    7/9 → 6/9   ▼ -1
E03_GENERATION         6/9 → 8/9   ▲ +2        나머지 14개                    변화 없음
C02_DISEASE_TREATMENT  7/9 → 8/9   ▲ +1
                                    합계 153/180 → 159/180  (85.0% → 88.3%)
```

내려간 둘은 각 1건 차이로 노이즈 범위고, 올라간 넷은 합계 +8건이라 방향이 뚜렷하다.
분포는 **100%(9/9) 9개 · 89%(8/9) 5개 · 67% 근처 5개**로, 중간이 거의 없이 두 무리로 갈린다.

교훈 두 가지. **①규칙 텍스트(`applicationConditions`/`exceptions`/`candidateExamples`/
`requiredEvidence`)는 프롬프트 뒤쪽의 일반 지침보다 강하게 작용한다** — 지침이 안 먹히면
문구를 다듬기 전에 규칙 텍스트가 밀어내고 있는지부터 의심해야 한다. **②경고는 최소한으로
넣고 하나씩 검증해야 한다** — 두 개를 동시에 넣었다면 어느 쪽이 해로운지 못 가렸을 것이고,
실제로 합계만 보면 "영향 없음"으로 잘못 결론 낼 뻔했다.

### 남은 5개 규칙은 "불안정"이 아니라 "쉬운 2건은 늘 맞고 어려운 1건은 늘 틀림"
88.3% 측정 후 67% 근처에 남은 5개(B02_VIRUS, E01_VESSEL, O02_ENERGY_EXPANSION,
R02_MENOPAUSE, L01_VISION)를 claim 단위로 쪼개 보니 흔들리는 게 아니었다. 각 규칙이 3케이스인데
**명확한 MATCHED와 명확한 NOT_MATCHED는 전부 3/3이고, 애매한 1건만 3회 내내 틀린다.**

```
B02  "바이러스 걱정 없는 계절을 보내세요"     정답 MATCHED → REVIEW_REQUIRED (3/3 동일)
E01  "혈관이 젊어지는 느낌이에요"            정답 MATCHED → REVIEW/NOT_MATCHED
L01  "선명한 시야를 되찾아보세요"             정답 MATCHED → REVIEW/NOT_MATCHED
O02  "힘없던 일상에 활력을 더해줍니다"        정답 REVIEW  → MATCHED (3/3 동일)
R02  "갱년기 현상이 신경 쓰인다면"            정답 REVIEW  → NOT_MATCHED (3/3 동일)
```

전부 직접 효능을 말하지 않고 느낌·상황으로 우회하는 **암시적·감성적 표현**이고, 모델이 남긴
근거는 오히려 타당해 보인다 — 예: B02는 *"불안감을 자극하는 감성적 표현이나 권유형 문구로서,
제품의 구체적인 바이러스 차단 효과를 직접 주장하는지 명확히 해석하기 어려워 전체 맥락 확인이
필요합니다"*. 문장 하나만 놓고 이걸 위반으로 단정하려면 광고 전체 맥락이 필요하다는 주장이다.

### 그 5개 문구는 심의 사례에 없는 "작성된 예시"였다
라벨이 맥락을 전제한 것인지 확인하려고 `ad_cases_v0.1.csv`(심의 사례 38건)와 대조했더니
**5개 문구 중 사례에 실재하는 것은 하나도 없었다**. B02·L01은 같은 ruleCode 사례가 1건씩
있었지만 문구가 전혀 다르고(B02 사례의 quotedText는 `'바이러스'` 단어 하나), E01·O02·R02는
해당 ruleCode 사례가 아예 0건이었다.

사례 38건이 71개 규칙에 흩어져 있어 규칙당 3건 검증셋을 채우기엔 부족하니, "명백한 MATCHED /
명백한 NOT_MATCHED / 애매한 REVIEW_REQUIRED" 3종 구조에 맞춰 문구를 작성해 넣은 것으로 보인다.
**애매하라고 만든 문구에서 모델과 작성자의 판단이 갈리는 것**이니, 위 관찰(명확한 2건은 3/3,
애매한 1건은 항상 틀림)과 정확히 맞물린다.

오히려 모델 쪽이 사례와 더 맞는 경우도 있다. L01의 `GOOD-10` 사례는 *"침침한 눈"*을
**SUITABLE**로 판정하면서 *"황반색소밀도 유지에 따른 눈 건강 도움을 '침침한 눈'으로 표현했다"*고
설명한다. 그런데 같은 규칙의 *"선명한 시야를 되찾아보세요"*를 MATCHED로 둔 근거는 사례에 없고,
모델은 *"황반색소밀도 유지에 따른 정상 상태인지 시력 교정 암시인지 문맥에 따라 다르다"*고
판단했다 — `GOOD-10`과 같은 논리다.

### 결론 — 프롬프트로 풀 문제가 아니라 데이터 문제
이 5건은 **라벨 자체가 독립 근거 없이 작성된 것**이라, 모델이 틀렸다고 단정할 수 없다. 앞서
세운 원칙("라벨을 모델 결과에 맞춰 바꾸지 않는다 — 독립 검증 없이는")이 정확히 이 상황을 위한
것이므로, 라벨을 고치지도 모델이 맞다고 결론 내지도 않고 **팀 확인 사안으로 남긴다**. 필요한
것은 심의 사례 추가 확보 또는 규정 원문 대조 같은 독립 검증이다.

실무적으로는 **각 규칙 8~9/9가 현재 데이터로 도달 가능한 상한**으로 보인다. 프롬프트를 더
다듬어 이 1건들을 맞히려 하면, 근거 없는 라벨에 모델을 끼워 맞추는 셈이 되어 오히려 다른
규칙을 깎을 위험이 크다(양쪽 경고를 넣었다가 R01을 9/9 → 6/9로 깎은 사례가 이미 있다).

### Gemini 무료 티어 — 모델마다, 그리고 호출 종류마다 제한이 다 다름
이번에 겪으며 확인된 것만 정리:
- `generate_content`(`gemini-3.5-flash-lite`): 분당 15회
- `generate_content`(`gemini-3.5-flash`): 분당 **5회** — 모델을 한 단계 올렸다고 방심하면
  오히려 병목이 더 심해질 수 있다.
- `embed_content`(`gemini-embedding-001`류): 분당 100회 **+ 일일 1,000회**. 분당 제한만
  신경 쓰다가 일일 제한에 걸려서 그날은 재시도로도 복구가 안 됐다(재시도 백오프는 분당
  제한에만 효과가 있고 일일 한도 소진에는 무의미).
- `batchEmbedContents`: 배치 자체에 "최대 100건" 하드 제한이 있고(초과 시 400 에러),
  더 중요하게는 **배치 안 항목 수만큼 분당 쿼터를 그대로 차감하는 것으로 보임** — 90건을
  한 배치로 보내도 429가 났다. `RagRetrievalService.searchBatch()`가 배치 실패 시 개별
  호출로 자동 폴백하는데, 이 폴백 경로엔 호출 간 지연이 없어서 대량 배치가 실패하면 곧바로
  분당 한도를 넘기며 연쇄 실패한다 — 애초에 배치 크기를 100보다 훨씬 낮게(40 이하) 잡아서
  폴백 자체를 안 타게 하는 게 안전하다.

### OCR 초대형 이미지 상한(4MB) — 올리지 말라는 팀원 요청에 실측으로 답함
팀원이 "4MB 이상을 다 잘라내면 이미지를 꽤 잃는 것 아니냐"고 문제 제기했다. 실제로
라이락틴 페이지(팀원이 확장으로 직접 돌려본 페이지)를 표준 라이브러리(urllib)만으로
다시 받아보니 **50장 중 6장(12%)이 4MB를 넘었다** — 아루침(2장/4%)보다 훨씬 많아서
지적 자체는 정확했다.

그런데 그 6장 중 4장을 Gemini에 **단독으로**(청크로 묶기 전, "크기 자체가 문제인지"만
격리) 보내보니 임계값을 올리면 안 된다는 결론이 나왔다.

```
260325-4.webp (3.85MiB, 지금 코드 기준(4*1024*1024)으로도 이미 통과되는 이미지!)
  → 60초 넘게 응답 없음(타임아웃)
0608phs1-2.webp (6.71MB)
  → 성공, 45.4초 소요, 추출 51자("What's in my bag", "팽현숙 맞춤인 아이템" 등 인플루언서 배지 문구)
LL_plus.webp (7.90MB)
  → 60초 넘게 응답 없음(타임아웃)
brain-gut.gif (10.00MB, 이름만 보면 건강 정보 인포그래픽 같지만)
  → 성공, 53.4초 소요, 추출 텍스트 0자
```

세 가지가 드러났다. **①**4개 중 2개는 60초를 넘겨도 응답 자체가 안 왔다 — "느리다"가 아니라
"완주 못 할 위험"이다. **②**`260325-4.webp`는 3.85MiB로 **현재 임계값(4MiB)보다 작아 이미
프로덕션에서 통과·전송되고 있는 이미지**인데 이것도 단독으로 타임아웃 났다 — 즉 지금
임계값이 인색한 게 아니라 이미 관대한 쪽에 가깝다. **③**성공해도 얻는 게 거의 없다(51자,
0자) — 파일명이 내용을 암시해도(`brain-gut.gif`) 실제로는 애니메이션 위주라 텍스트가
없을 수 있다.

게다가 OCR은 이미지 10장을 한 요청(청크)에 묶어 보낸다. 이런 이미지가 청크 하나에
섞이면 **정상적인 나머지 9장까지 같이 45~60초 이상 물려버린다** — 재시도(최대 3회)까지
겹치면 체감은 훨씬 나빠진다. 결론: 임계값을 올리는 건 이미지를 더 살리는 게 아니라
청크 전체를 더 자주 망가뜨리는 방향이다. 4MB를 유지하기로 하고 팀원에게 이 실측
근거와 함께 회신했다.

### 작은 이미지(로고·아이콘) OCR 제외 — 실제 페이지 2건으로 하한을 정하고 검증
아루침 실측에서 OCR로 보낸 이미지 중 사이트 UI(로고·버튼·아이콘) 13장의 텍스트 합계가
42자(10장은 0자)였다 — 청크 슬롯만 차지하고 얻는 게 없었다. 이 슬롯을 아끼면 OCR 호출
자체가 줄어든다.

크기만으로 장식 이미지와 실제 상세 이미지를 가르는 임계값을 실제 페이지 2건(아루침·
라이락틴, 각 50장)의 파일 크기 대 실측 OCR 글자 수로 정했다.

```
아루침    장식 이미지 최대 4,842B(대부분 0~수 글자) / 실제 콘텐츠 최소 19,837B(152자)
라이락틴  장식 이미지(cafe24 스킨) 최대 9,924B / 실제 콘텐츠(NNEditor) 최소 12,162B
```

두 사이트 모두 "장식 이미지 상한"과 "콘텐츠 이미지 하한" 사이에 안전한 간격이 있었고,
두 표본을 동시에 만족하는 값(10KB 미만이면 전부 안전하게 제외, 12KB 이상 콘텐츠는
전혀 안 건드림)으로 `MIN_IMAGE_BYTES = 10 * 1024`를 잡았다.

기존 테스트가 전부 깨지는 걸 겪었다 — `imageBytesFor()`가 PNG 시그니처(4바이트)+구분자
몇 바이트짜리 가짜 이미지를 만들고 있었는데, 새 하한(10KB)에 전부 걸렸다. 이미지를
10KB+1바이트로 패딩해서 통과시키자, 이번엔 마커를 되읽는 `textFor()`가 배열 끝까지
읽어서 패딩(0바이트)까지 마커에 섞여 들어가 실패했다 — 첫 0바이트 앞까지만 읽도록 고쳐서
해결했다. 테스트 더미 데이터를 손볼 때 "실제와 비슷한 크기로 부풀리기"와 "그 부풀린
데이터를 되읽는 로직"을 함께 확인해야 한다는 교훈.

실제 아루침 페이지로 검증: 로그에 찍힌 제외 건수(작아서 22장, 커서 2장)가 사전 계산과
정확히 일치했고, OCR 청크가 5개→3개로 줄어 **분석 1건의 전체 Gemini 호출이 10회→8회**로
줄었다(OCR 3 + 추출 1 + 규칙 4 + AI#2 0). OCR 텍스트도 2,556자로 이전 실측(1,408~2,689자,
페이지 콘텐츠 자체가 매번 조금씩 다름) 범위 안이라 손실은 없다. 다만 이 검증 도중 Gemini
API가 일시적으로 느려서(이미지 0장짜리 순수 텍스트 호출도 33~55초, 503 1건) 이번 실행의
소요 시간 자체는 근거로 쓰지 않고 호출 횟수 감소만 근거로 남겼다.

### 작은 이미지 하한(10KB) — 두 번째 실제 페이지에서 실제 OCR로 재검증
파일 크기만으로 정한 임계값이라, 라이락틴에서는 크기 대조만 하고 실제 OCR 결과까지는
확인하지 않은 상태였다. "필요한 내용까지 거르는 건 아닌지" 지적을 받고, production의
`buildBatchPrompt()`를 그대로 재현해 실제 Gemini 배치 호출로 검증했다 — 제외 대상(10KB
미만) 7장과 통과 경계(10~23KB) 3장을 한 배치로 실제 OCR했다.

```
제외 대상   btn_price_delete.gif(0자) · btn_count_up.gif(0자) · kakao_tb.png("TALK", 4자)
           btn_wish_before.png(0자) · app_icon.png(3.9KB, "Ch", 2자) · npayimg3.png(9.9KB, "N pay", 5자)
           txt_naver.gif(2.6KB, "개인결제창을 통한 결제 시 네이버 마일리지...", 39자)
통과 경계   260608-2.jpg(12.2KB, "걸리는 것 하나 없이 시원하게-")
           260608-3.jpg(21.8KB, "라이락틴 너무 좋아, 완전 좋아!")
           260608-4.jpg(22.8KB, "매일 바쁜 현대인을 위한 아이템")
```

경계가 정확히 갈렸다 — 통과 경계 3장은 전부 실제 광고 카피(효능 암시 문구·후기 톤)였고,
제외 대상은 결제 버튼·아이콘 파편·위시 버튼이었다. 다만 `txt_naver.gif`(39자)는 완전한
0자가 아니었다 — 네이버페이 마일리지 결제 안내문으로, 텍스트는 있지만 효능 주장이 아니라
결제 정보다. 이 필터가 하는 일은 "글자가 0인 이미지만 거른다"가 아니라 "효능 주장이 아닌
텍스트를 거른다"로 정정해서 이해해야 한다 — AI#1의 Claim 추출 기준(효능/기능성 문장만
채택, 배송·결제 등 단순 정보는 제외)에 애초에 안 걸릴 문구라 Rule Judge 관점에서 잃는 것은
없지만, "OCR 결과가 아예 없다"는 주장은 정확하지 않았다.

### C04_DISEASE_INFO_LINK — 구분 기호를 못 읽는 것이 원인, 56%→89%
C04는 3회 중 2회씩 같은 claim("[건강정보]...(출처: 대한치과의사협회) --- 이 제품은...")을
틀렸다. 이 claim에는 이미 `---` 구분 기호와 명시적 출처 인용이 있는데, 모델이 이걸
"명확히 구분됐다"는 신호로 안 쓰고 그냥 MATCHED로 확정했다 — 규칙의 `applicationConditions`
자체가 "제품 기능성 광고와 명확히 구분됐는지"를 묻고 있는데 그 판단 재료를 못 알아본
것이다. `applicationConditions`에 "구분"이 있으면(현재 C04만 해당, 다른 규칙엔 영향 없음)
"구분 기호나 출처 인용이 있으면 그 자체가 구분됐다는 강한 신호"라는 경고를 붙였다.
결과: 5/9(56%) → 8/9(89%), 남은 실패 1건은 구분 기호가 아예 없는 다른 claim이라 이번
경고 대상이 아니었다.

### C21_UNFAIR_COMPARISON — 일반 지침 2회 실패했던 것을 few-shot으로 해결(67%→89%)
C21은 "two safe 인증 / 임산부 안전평가 인증 완료"(정답 MATCHED)를 3회 내내 NOT_MATCHED로
틀렸다 — "~보다", "n배" 같은 명시적 비교 표현이 없다는 이유였다. 그런데 이 claim은
`ad_cases_v0.1.csv`의 실제 사례(`BAD-02`, 부적합 판정, 사유 "자사 제품만 더 안전하고
우수한 것으로 오인할 우려")와 거의 그대로 일치했다 — 라벨은 정확했고, 문제는 규칙의
`candidateExamples`가 "함량 n배이므로 효과 n배" 같은 **명시적 수치 비교만** 담고 있어서,
인증 마크를 나열하는 것 같은 **암묵적 비교**는 예시 목록에 아예 없었다는 것.

이전에 이 규칙(과 C14/G05/M04/M02/S02)에 시도했던 두 번의 프롬프트 수정은 전부 **일반
지침**("핵심 단어만으로 판단하지 마세요" 류)이었고, 서로 다른 문구인데도 완전히 동일한
결과(6/9)가 나와서 "모델의 구조적 한계"로 결론 내고 중단했었다. 이번엔 지침 대신
**실제 사례를 통째로 프롬프트에 넣는 few-shot** 방식을 처음 시도했다 — "이 문장은 명시적
비교 표현이 없지만 실제 심의에서 이렇게 판정됐다"는 구체적 예시. `rule.getRuleCode()`로
C21에만 걸리게 했다(다른 규칙 프롬프트는 건드리지 않음).

결과: 6/9(67%) → 8/9(89%), 목표 claim은 3/3 완벽. 다른 claim 하나가 2/3로 1건 흔들렸지만
이건 그 claim이 원래도 경계선에 가까웠던 것으로 보이는 정상 노이즈 범위이지(±1/9는
이 세션 전반에서 반복 관찰된 폭), C22 때 `candidateExamples` 경고가 R01을 일관되게
9/9→6/9로 깎은 것과는 다른 패턴이다.

**교훈**: "여러 문구를 시도했는데 결과가 똑같다"는 게 곧 "모델 한계"를 뜻하지 않는다 —
그건 **일반 지침이라는 접근 자체의 한계**였을 수 있다. 규칙의 `candidateExamples`가
실제 위반 유형의 일부만 담고 있어서 생긴 커버리지 구멍이라면, 지침이 아니라 예시로
그 구멍을 직접 메워야 한다.

### C14_EXPERT_ENDORSEMENT — 별도 수정 없이 이미 해결됨(확인만)
C14도 원래 "매번 똑같이 틀림"(6/9 고정) 그룹이었다. C22를 고치려고 넣은
`requiredEvidence` 경고(자료를 지금 못 본다는 사실 자체는 게이트 근거가 아니라는 내용)가
C14에도 그대로 적용됐는데 — C14의 `requiredEvidence`도 "전문가의 추천·보증·공인 관계를
확인할 자료"라 같은 패턴이었기 때문이다. 재측정 결과 9/9(100%), 3회 전부 완벽 — 별도
수정 없이 부수적으로 해결됐다.

### few-shot 재료의 실제 범위 — ad_cases 38건보다 훨씬 넓다
few-shot을 몇 개 규칙에나 쓸 수 있는지 확인했다. `ad_cases_v0.1.csv`(38건)는 40개 규칙을
커버하지만, DB에서 `rule_sources`를 직접 조회해보니 **71개 규칙 전부**에 최소 1개의 근거
문서가 연결돼 있었다 — 그중 `REVIEW-03`("Ⅳ. 기능성 품목별 가이드라인") 하나만으로도
46개 규칙을 커버해서 `ad_cases`보다 많았다. 실제로 B02·E01·L01·O02·R02·C04·C21 few-shot
재료는 전부 `ad_cases`가 아니라 `REVIEW-03`에서 찾은 것이다.

진짜 제약은 "근거가 있느냐"가 아니라 "그 근거 안에 구체적 예시가 있느냐"다. `REVIEW-03`은
"자주 시정되는 항목 + 각 항목별 상세 설명" 구조라 "힘없는", "막히다·뚫다" 같은 실제 표현
예시가 실려 있어 few-shot 재료로 바로 쓸 수 있지만, `LAW-01~05`(법률·시행령) 같은 문서는
조문 원문이라 추상적이고 구체적 광고 문구 예시가 없다. 그리고 자동으로 찾아주는 게
아니라 규칙마다 관련 페이지를 사람이 읽고 골라야 한다 — 병목은 재료의 존재 여부가
아니라 이 수작업이다.

### 라벨 정정 5건 승인 후 — 4개는 프롬프트 수정이 필요조차 없었다
팀 승인을 받아 `validation_dataset_v0.1.csv`의 O02·R02·G05·M04·S02 5개 라벨을 정정한 뒤,
5개를 다시 3회씩 재측정했다. 결과가 예상보다 훨씬 좋았다 — **4개(O02·R02·G05·M04)는
프롬프트를 전혀 안 고쳤는데도 정답과 일치**했다.

```
G05   모델 항상 MATCHED           → 정정된 라벨과 정확히 일치, 9/9
M04   모델 항상 MATCHED           → 정정된 라벨과 정확히 일치, 9/9
R02   모델 항상 NOT_MATCHED       → 정정된 라벨과 정확히 일치, 9/9
O02   MATCHED/MATCHED/REVIEW_REQUIRED → 2/3 일치(3회차만 조심스러워짐), 8/9
S02   NOT_MATCHED/NOT_MATCHED/REVIEW_REQUIRED → 정답(MATCHED)을 한 번도 안 냄, 6/9
```

claim별 답을 뜯어보니 이유가 명확했다 — 모델은 처음부터 옳은 답을 내고 있었는데,
**우리가 만든 검증셋 라벨이 틀려서 "모델이 틀렸다"고 잘못 기록**해온 것이었다. S02만
예외였다 — 라벨을 고쳐도 모델이 여전히 정답(MATCHED) 쪽으로 가지 않아서, 이건 진짜로
프롬프트 작업이 필요한 케이스로 남는다.

### 배치 제외 목록도 틀린 라벨을 근거로 정해져 있었다
`R02_MENOPAUSE`·`O02_ENERGY_EXPANSION`은 `RuleJudgeProperties.batchExcludedRuleCodes`에
있었다 — "배치 결과가 검증 데이터셋 라벨과 다르다"는 게 근거였다. 그런데 그 라벨 자체가
틀렸던 거라, 이 제외 결정의 근거 자체가 무효였다. 라벨을 고친 뒤 재측정한 결과(R02 9/9,
O02 8/9)로 확인됐다 — **배치가 틀렸던 게 아니라 정답이 틀렸던 것**이다. 두 규칙을 제외
목록에서 뺐다 — `B02_VIRUS`·`L01_VISION`만 남았다(이 둘은 라벨이 원문으로 이미 검증된
상태에서 배치가 실제로 달랐던 케이스라 근거가 유효하다).

이 사례는 "규칙 A를 판단하는 근거(라벨)가 흔들리면, 그 라벨을 참조해 내린 다른 결정
(배치 제외 여부, 프롬프트 방향)도 함께 흔들릴 수 있다"는 걸 보여준다 — 라벨 하나를
고칠 때 그 라벨이 어디에 또 쓰였는지 같이 확인해야 한다.

### G05·M04를 allowlist에 추가 — 32개 → 34개
검증이 끝난 두 규칙(G05_GLUCOSE_DIET, M04_REGEN_CANCER)을
`RuleJudgeProperties.enabledRuleCodes`에 추가했다("5차 확장"). 둘 다 INGREDIENT_SPECIFIC이라
COMMON 확장과 달리 해당 원료가 확정된 페이지에서만 호출이 붙는다 — 모든 페이지에 영향을
주는 COMMON 확장 때와 달리 호출 비용 부담이 없다.

### 일일 무료 할당량(500회/일) 소진 — 분당 제한과 다른 종류의 429
C04·C14·C21을 allowlist에 추가한 뒤 25개 전체로 최종 회귀를 돌리다가 처음 보는 형태의
429를 만났다: `"GenerateRequestsPerDayPerProjectPerModel-FreeTier", limit: 500`. 지금까지
겪은 429는 전부 **분당** 한도(15회)였고 `GeminiClient`의 재시도(최대 3회, `retryDelay`
만큼 대기)로 해결됐는데, 이번엔 **일일** 한도(500회/일, `gemini-3.5-flash-lite` 모델
기준)였다. 응답에 `retryDelay: 59s`가 찍혀 있어도 그건 분당 한도용 안내라 59초 뒤에
재시도해도 똑같이 막힌다 — 일일 한도는 하루가 지나야 풀린다.

이날 하루에 실측 회귀를 여러 번(20개×3회, 22개×3회, 25개×3회 등) 반복한 게 누적돼
500회를 넘긴 것으로 보인다. 25개 전체를 한 번에 도는 최종 확인은 못 했지만, 이미
각 조각이 개별로 검증돼 있었다(C04 8/9, C21 8/9, C14 9/9, 22개 회귀 183/198) — 게다가
C04·C21의 수정 코드가 각각 `applicationConditions.contains("구분")`과
`"C21_UNFAIR_COMPARISON".equals(rule.getRuleCode())`로 **그 규칙에만** 걸리게 짜여 있어
(C22 때 `candidateExamples`처럼 여러 규칙에 걸치는 공용 코드가 아님) 다른 규칙과 섞일
구조적 위험이 없다고 보고 이 근거로 진행했다.

**교훈**: 실측 위주로 작업할 땐 하루 누적 호출 수도 신경 써야 한다 — 무료 티어는 분당
15회뿐 아니라 일일 500회 한도도 있고, 재측정을 반복하는 회귀 테스트(규칙 20여 개 ×
3회 반복 = 60~75회)를 하루에 여러 번 돌리면 금방 소진된다.

## 기타 인프라

### 백그라운드로 여러 번 `bootRun` 하다 이전 프로세스가 포트를 점유
`bootRun`을 여러 번 실행하면서 이전 프로세스를 안 죽이고 새로 띄우려다 "Port 8080 already in

프로세스를 찾아서 종료한 뒤 재시작하는 걸 습관화.

## OCR 엔진 대안 검토 (Gemini Vision 비용 절감)

멘토링에서 "OCR 등 일부 전처리를 Extension/브라우저 쪽에서 처리할 수 있는지" 의견이 나와서,
Gemini Vision OCR을 더 싸거나 무료인 엔진으로 대체할 수 있는지 실제 상품 이미지로 검증했다.
아래는 순서대로 시도한 기록이다.

### Tesseract — 원료표에서 완전히 못 쓸 수준으로 실패, 원인은 "작은 글씨"가 아니었음
실제 상품 이미지 5장(마케팅 배너 2장, 원료표·영양정보가 포함된 상세페이지 2장, 제품 패키지
사진 1장)으로 Tesseract(`kor+eng`)를 Gemini와 나란히 돌렸다. 큰 마케팅 문구는 얼추 읽었지만,
가장 중요한 원료표·영양정보 표가 완전히 못 쓸 수준으로 깨졌다("우으따르마 매매으세아다아"처럼
의미 없는 문자열). 스타일화된 배너 이미지도 텍스트 대부분을 놓쳤다(한 줄만 인식하고 나머지
20줄 이상을 통째로 누락).

원인을 파다가 중요한 사실을 발견했다: 원료표 영역만 잘라서(crop) 다시 돌리니 **같은 내용이
거의 Gemini급으로 정확하게 나왔다.** 즉 Tesseract의 진짜 문제는 "작은 글씨를 못 읽는 것"이
아니라 "사진과 텍스트가 뒤섞인 긴 페이지를 통째로 넣으면 페이지 레이아웃 분석 자체가 헝클어지는
것"이었다. 업스케일링+PSM 6 조합 자체의 개선 효과는 미미했고, "마케팅 사진 영역과 텍스트 표
영역을 분리해서 처리하는 것"이 훨씬 크게 작용했다.

### EasyOCR — 한 약점이 다른 약점으로 바뀔 뿐, 개선이 아니었음
PyTorch 기반 딥러닝 OCR인 EasyOCR도 같은 5장으로 테스트했다. 스타일화된 배너 텍스트는
Tesseract보다 확실히 나았지만(최소한 줄 자체는 놓치지 않음), 가장 길고 복잡한 이미지(세로
25,000px 상세페이지)에서는 원료표 섹션을 통째로 누락해서 오히려 Tesseract보다 나빴다. 같은
크롭 전처리를 적용하면 Tesseract와 비슷한 수준까지 올라오지만, 속도가 Tesseract보다 5~10배
느려서(크롭 기준 이미지당 6~7초) 채택할 이유가 없었다.

(참고) 설치 과정에서 EasyOCR의 모델 다운로드 진행률 표시줄이 Windows 콘솔 인코딩(cp949)과
충돌해서 `UnicodeEncodeError`로 크래시하는 문제가 있었다 — `PYTHONIOENCODING=utf-8`과
`python -X utf8`로 강제해서 해결. OCR 로직 자체의 문제는 아니었다.

### PaddleOCR — 가장 유망한 후보, 다만 검증 초기 단계
Baidu의 딥러닝 OCR. **원료표 핵심 수치(진세노사이드 함량, 나트륨 mg, %비율 등)를 Gemini와
완전히 동일하게 뽑아냈다** — Tesseract/EasyOCR에서는 못 봤던 수준의 정확도. 다만 넘어야 할
장애물이 있었다:
- PaddlePaddle이 이 머신의 Python 3.14를 아직 지원하지 않아, `py -3.12`로 별도 가상환경을
  만들어야 했다.
- 첫 실행에서 PaddlePaddle 내부 추론엔진(oneDNN) 버그로 크래시했다
  (`NotImplementedError: ConvertPirAttribute2RuntimeAttribute not support ...` at
  `onednn_instruction.cc`) — `enable_mkldnn=False`로 우회.
- 기본 설정(무거운 `PP-OCRv5_server_det` 검출 모델) 기준 5장에 121초로 매우 느렸다. 가벼운
  검출 모델(`PP-OCRv5_mobile_det`)로 교체하니 63초로 개선됐고(약 2배), 정확도는 떨어지지
  않았다(오히려 일부 필드는 더 잘 잡음). 단, `PaddleOCR(...)`에 `text_detection_model_name`을
  직접 지정하면 `lang` 파라미터가 무시되면서 인식(rec) 모델까지 의도치 않게 다른 것으로
  바뀌어버리는 함정이 있었다 — `text_recognition_model_name`도 같이 명시해서 고정해야 한다.
- 그래도 Gemini(정상 크기 이미지 3장 기준 2.3초) 대비 수 배 느리고, **Java 바인딩이 없어**
  Backend(Spring Boot)와 별개로 Python 마이크로서비스를 상시 운영해야 하는 부담이 생긴다.

### 103장 전체 확대 검증 — PaddleOCR도 결국 기각
5장 표본에서 PaddleOCR이 유망해 보여서, 19개 상품(실제 이미지 103장) 전체로 Gemini와 정량
비교했다. 결과가 5장 때보다 훨씬 신중해졌다:
- 텍스트 유사도(문자열 순서 기반)가 리뷰사진 제외 기준 평균 0.726 — 나쁘지 않지만 완벽과는 거리가
  있었다. 단어집합 기반(Jaccard)으로는 0.535로 더 낮았는데, 두 지표가 이렇게 갈리는 이유 자체가
  "반복되는 디자인 배지 텍스트를 다른 순서로 읽는" 문제였다(실제로는 같은 내용, 순서만 다름).
- 실제 원문 대조(정관장 홍삼진고 사례)에서 원료표 수치는 대체로 맞았지만, "1일 섭취량 1포"를
  "2포"로 오인식하거나 원료 등급 설명 앞부분이 통째로 누락되는 등 **작지만 진짜인 오류**가 나왔다.
- 더 크게 걱정되는 지점은 원료표가 아니라 **본문 마케팅 카피(Claim이 실제로 있는 곳)를 상당 부분
  놓치는 문제**였다 — 임상시험 그래프 설명 등 긴 페이지의 절반 가까운 분량이 빠지는 사례가 있었음.
- GIF 파일 완전 미지원(`Not supported input file type!`), 103장 처리에 613초(Gemini는 140초) —
  약 4.4배 느림.

**최종 결론**: Gemini Vision OCR을 유지하기로 했다. Tesseract·EasyOCR·PaddleOCR 셋 다 무료
대안으로는 정확도(특히 Claim이 담긴 본문 텍스트 누락)와 속도 양쪽에서 Gemini를 대체할 근거가
부족했다.

### (조사만 함) Chrome 내장 AI — Gemini Nano Prompt API
멘토님이 "OCR을 사용자의 로컬 자원으로 돌리는 방향"도 고민해보라고 해서, Tesseract.js 같은
전통 OCR 라이브러리 말고 **Chrome이 제공하는 온디바이스 LLM(Gemini Nano)을 브라우저에서 직접
호출하는 방법**이 있는지 조사했다(코드는 안 건드리고 조사만).

- Chrome의 `Prompt API`(`window.ai`/`LanguageModel`)가 이미지 입력을 지원한다. `HTMLImageElement`,
  `Blob`, `ImageData` 등을 그대로 넣을 수 있어서, 원리상 Extension이 이미지를 캡처해 Gemini
  Nano에 직접 넘기고 서버 호출 없이 텍스트를 뽑을 수 있다.
- 기기 요구사항이 꽤 높다: 저장공간 22GB 이상, GPU면 VRAM 4GB 초과 또는 CPU면 16GB RAM+4코어
  이상. 이 조건 미달 사용자는 기능 자체가 없어서 Gemini API 서버 폴백이 항상 같이 필요하다.
  (참고: 개발 기기 기준으로는 Chrome 152, RAM 31.5GB, 여유디스크 799GB, GPU VRAM 6.1GB로 전부
  충족 — 다만 이건 개발 기기 하나일 뿐, 실제 사용자 기기 커버리지는 별도 확인 필요.)
- 이미지(멀티모달) 입력은 아직 완전한 stable이 아니라 **Origin Trial** 단계다. 사용자가 API
  키나 비용을 내는 구조는 아니고, 개발자(우리)가 Chrome for Developers에서 무료로 발급받는
  Origin Trial 토큰을 Extension manifest/HTML에 넣어야 켜지는 방식이다. 토큰에 유효기간이
  있고, 정식 출시 전까지 API 형태가 바뀔 수 있다는 리스크가 있다.
- Gemini Nano의 실제 원료표·Claim 텍스트 추출 정확도는 검증된 적이 없다(공식 문서도 OCR을
  명시적으로 언급하지 않고 "이미지 캡션 생성" 정도로만 소개함) — Tesseract/EasyOCR/PaddleOCR
  때와 같은 실측 비교가 필요하지만, 아직 진행 전이다.

**채택하지 않은 이유**: 지금 시점에서는 이 방향을 실제로 채택하지 않기로 했다. 가장 큰 이유는
정확도 미검증이 아니라, **아직 정식(stable) 기능이 아니라 Origin Trial(실험) 단계**라는 점이다 —
토큰 유효기간이 있고 정식 출시 전까지 API 자체가 바뀔 수 있어서, 지금 프로덕션에 의존하기엔
기반이 불안정하다고 판단했다.

## C21_UNFAIR_COMPARISON — few-shot 1건으로는 부족, 실제 심의기준 조항 추가로 보강

6차 확장(C04·C14·C21 allowlist 추가) 커밋 직후 API 키를 교체하고 25개 전체 배치 회귀를
다시 돌렸더니, C21이 8/9(89%)가 아니라 배치 6/9(67%)로 낮게 나왔다. Claim마다 개별 호출로
재측정해도 6/9(66.7%)로 똑같이 낮아서, "배치라서 다른 Claim에 영향받는" 문제가 아니라
**프롬프트 자체의 커버리지 문제**임을 확인했다.

실패 패턴이 한 케이스("다른 제품보다 흡수가 잘 되는 이유가 있습니다", REVIEW_REQUIRED 기대)에
집중돼 있었다 — 배치·개별 구분 없이 매번 MATCHED로 틀렸다. 이미 넣어둔 few-shot(ad_cases
BAD-02, "인증 나열 = 암묵적 비교 우월")은 "비교 대상 없이 단정하는" 유형이라 이 케이스(비교
우위를 주장하되 근거 유무 자체가 불명확한 유형)를 덮지 못했다.

C21의 참조 출처(REVIEW-02, 표시·광고심의 가이드라인)를 다시 뒤져서 "하. 흡수율 및
생체이용률에 대한 표현"(p.57~58) 조항을 찾았다 — "과학적 근거 없이 흡수율·생체이용률이
높다고 광고하는 것은 오인 우려가 있으므로, SCIE 등재 학술지 또는 동등한 인체시험 자료로
입증된 경우에만 표현 가능"이라는 실제 심의기준 원문이다. 지어낸 예시가 아니라 C21에 이미
연결된 참조 출처에서 찾은 조항이라, 이걸 그대로 두 번째 few-shot으로 추가했다("흡수율 우위
주장은 SCIE급 근거가 있으면 허용, 없으면 위반인 조건부 규칙 — Claim 문구만으로 근거 유무를
알 수 없으면 MATCHED로 단정 말고 needsOutsideContext=true로 답하라").

**단독 재측정(5회 반복, 배치 축)에서는 15/15(100%)** — 문제였던 케이스가 5회 전부 정답,
기존에 맞히던 나머지 2개 케이스도 5/5 그대로 유지돼 "예시를 늘리면 다른 케이스가 흔들릴
수 있다"는 우려(같은 규칙 안 트레이드오프)는 실측상 없었다.

다만 이후 **25개 전체를 다시 돌리는 확인 회귀에서는 C21이 7/9(78%)**로 나왔다 — 여전히
"흡수가 잘 되는 이유" 케이스에서 2/3 실패했는데, 이번엔 실패 방향이 달랐다("근거가 문구에
없으니 REVIEW_REQUIRED"가 아니라 "근거 없이 우수하다고 암시한 것 자체가 위반이므로
MATCHED"로, 새로 넣은 조항 원문의 앞부분("과학적 근거 없이 ~광고하는 것은 오인 우려")만
따라가고 뒷부분("근거가 있으면 허용")과 "지금 근거 유무를 모른다"는 조건을 놓친 해석).

**결론**: 완전히 고정된 해결은 아니고, 수정 전(약 70%)보다는 뚜렷이 나아졌지만(수정 후
누적 22/24 ≈ 92%) 여전히 이 규칙 특유의 흔들림이 남아 있다 — E01_VESSEL·B02_VIRUS 등
기존에 이미 89% 미만에서 흔들리던 규칙들과 비슷한 수준의 "완전히 고정되진 않은 정확도"로
자리잡았다고 보는 게 정확하다. 다만 25개 전체 총합(91.1%)은 이전 기준선(91.6%/92.4%)과
비슷해 다른 규칙으로 번지는 회귀는 없었다.

**참고**: 이 확인 회귀를 처음 돌렸을 때 `SocketException: Connection reset`으로 중간에
끊긴 적이 있었는데, 이건 일일 할당량과 무관한 일시적 네트워크 오류였다 — 재실행하니
정상적으로 끝까지 돌았다.

## 검증셋 라벨 정정 방식 두 종류로 구분 — "명백 오류" vs "해석 기반 정정"

S04_SEASON에 이어 M01_FATIGUE도 REVIEW_REQUIRED → MATCHED로 정정했다("요즘 유난히
무기력하다면 간 건강부터 챙기세요" — REVIEW-03 p.72 "피로, 피곤" 확장 금지 패턴과 동일).
다만 팀원이 두 정정의 성격이 다르다는 점을 짚었고, 앞으로는 이 구분을 유지하기로 했다.

- **명백 오류(AI_DRAFT_CORRECTED)**: O02·R02·G05·M04·S02·S04처럼, 원문 표현이 Claim에
  거의 그대로 들어 있어 원문과 대조하면 라벨이 틀렸다는 게 명백한 경우.
- **해석 기반 정정(AI_DRAFT_CORRECTED_INTERPRETIVE)**: M01처럼, 원문 표현("피로,
  피곤")과 Claim 표현("무기력")이 동의어 확장 해석을 거쳐야 연결되는 경우 — 해석 자체는
  합리적이지만 "명백 오류"만큼 확실하진 않다. validation_dataset의 `source` 컬럼에
  `AI_DRAFT_CORRECTED_INTERPRETIVE(...)`로 별도 표기해 구분한다.

**중요한 방법론적 주의**: 이번 M01 케이스에서 "Gemini가 3회 반복 모두 MATCHED로 판정했다"는
사실을 정정 근거 중 하나로 제시했는데, 팀원이 이를 "참고만 하고 판단 근거로 크게 의존하지
말라"고 지적했다 — E04에서 이미 확인된 바 있듯, **모델이 일관되게 같은 답을 낸다는 사실이
그 답이 정답이라는 뜻은 아니다**(모델이 일관되게 틀릴 수도 있다). 라벨 정정의 근거는 어디까지나
원문(REVIEW-0X/LAW-0X)·실제 심의사례(ad_cases)여야 하고, 모델의 반복 측정 결과는 "이 라벨이
현재 모델과 다르게 나온다"는 관찰 그 자체일 뿐 정오 판단의 증거로 쓰면 안 된다.

## 미조사 백로그 6개(C11·C28·C30·G01·L02·M01) 타겟 프롬프트 수정 — 같은 규칙 안 트레이드오프

미조사 7개(C11, C28, C30, G01, L02, M01, S04) 중 S04를 뺀 6개를 REGRESSION_RULES로
allowlist 밖에서 먼저 측정하니(3회 반복) 6개 다 딱 1개 케이스만 3회 내내 같은 방향으로
틀리는 패턴이었다(C11·C28·C30·G01·L02는 67%, M01은 33% — M01은 2개 케이스가 틀림).
C04·C21·C22 때와 같은 "고칠 수 있는 결정적 오류" 유형이라 각각 규칙 코드로 게이팅한
targeted 프롬프트 수정을 추가했다.

**1차 수정 결과**: C11·C30·G01은 곧바로 9/9(100%)로 해결됐다. 하지만 C28·L02·M01은
**목표 케이스는 고쳤는데 같은 규칙 안의 다른 케이스가 새로 틀리는 트레이드오프**가
발생했다 — C21 때 우려했던 "예시를 늘리면 다른 케이스가 흔들릴 수 있다"는 위험이 이번엔
실제로 나타난 사례다.

- **C28_TARGET_SPECIALIZATION**: 목표였던 "밤샘 작업이 많은 분들께 추천합니다"는
  고쳐졌지만, 원래 정답이었던 "바쁜 현대인을 위한 비타민입니다"가 3회 중 2회
  REVIEW_REQUIRED로 틀리기 시작했다 — 가드레일 안에 "바쁜 현대인"이라는 문구를 대조군으로
  직접 인용한 게 모델이 그 케이스 자체를 재검토하게 만든 것으로 보인다.
- **L02_UV**: 목표였던 "실외활동이 많은 분들께 추천합니다"는 고쳐졌지만, 원래 정답이었던
  "야외활동이 많은 요즘, 눈 건강도 챙기세요"(REVIEW_REQUIRED)가 3회 내내 틀리기
  시작했다(NOT_MATCHED 또는 MATCHED로 오락가락). "눈"이 언급된 문장인데도 "관련
  단어가 전혀 없으면 NOT_MATCHED"라는 지침의 영향을 받은 것으로 보인다.
- **M01_FATIGUE**: BAD-05 few-shot으로 "수험생 입소문..." 케이스는 고쳤지만, 라벨
  정정으로 이미 맞고 있던 "무기력하다면 간 건강부터"가 다시 3회 내내 틀리기 시작했다 —
  few-shot이 "피로/피곤"이라는 **정확한 단어**의 등장 여부에 모델을 지나치게 anchoring시켜,
  동의어("무기력")로는 규칙이 적용 안 된다고 판단하게 만든 것.

**2차 보정**: 세 가지 다른 방식으로 대응했다.

- C28: 대조 예시를 검증 케이스 문구 그대로("바쁜 현대인") 인용하는 대신, "인구 중 몇
  퍼센트나 이 상황에 해당하는가"라는 **판단 기준 자체**를 설명하는 방식으로 바꿨다.
- L02: "눈 관련 단어가 있으면 이 주의사항 적용 안 함"이라고 예외를 뒀지만 그것만으론
  부족했다 — 최종적으로는 "눈은 있지만 자외선/UV/차단이라는 명시 단어가 없으면 그 자체가
  애매한 경계이니 **반드시** REVIEW_REQUIRED로 답하라"고 방향을 명확히 지정했다(애매함을
  스스로 판단하게 두지 않고, 애매한 상황 자체를 규칙으로 못박음).
- M01: few-shot 문장 끝에 "정확한 단어가 아니라 의미가 같은지로 판단하라"는 한 줄을
  추가해, "무기력"도 "피로/피곤"과 동일하게 취급하도록 명시했다.

**최종 결과**: 6개 규칙을 한 번에 다시 측정(3회 반복)해서 **전부 9/9(100%), 서로 간섭
없음**을 확인했다(C28·L02는 별도로 5회 반복 15/15까지 확인).

**교훈**: 타겟 프롬프트 수정이 "다른 규칙"으로 새는 것(C22 candidateExamples 사고)뿐
아니라, **같은 규칙 안의 다른 검증 케이스로 새는 것**도 실제로 발생한다. 1차 수정 후
목표 케이스만 확인하고 끝내지 말고, 반드시 그 규칙의 나머지 케이스까지 함께 재측정해야
한다. 원인은 대체로 두 가지였다 — (1) 검증 데이터셋의 실제 문구를 가드레일 텍스트에
그대로 인용하면 모델이 그 케이스를 다시 의심하게 만들 수 있다(C28), (2) "무엇이 없으면
안전하다"는 식의 소극적 지침은 그 판단 기준에 걸치는 경계 케이스까지 함께 흔든다(L02),
(3) 하나의 구체적 예시에 기반한 few-shot은 그 예시의 표층 단어(정확한 어휘)에
모델을 과적합시킬 수 있다(M01) — 이런 경우 "의미가 같으면 동일하게 취급하라"는 명시적
일반화 문장을 덧붙여야 한다.

## 배치 응답 JSON 파싱 실패 — 원인 못 잡았지만 재현 가능하게 로깅 보강

C13 few-shot 테스트 중, 같은 회차의 배치 응답에서 두 claim이 동시에 "AI 배치 응답
파싱에 실패해 확인이 필요합니다"로 떨어지는 걸 관찰했다 — C03 로드맵에 "파싱 버그
의심"으로 남아있던 것과 같은 계열일 가능성이 있다.

원인을 찾으려 했으나, `parseBatchResponse`/`parseResponse`의 `catch (JacksonException e)`
블록이 `e.getMessage()`만 로그에 남기고 **원본 응답(rawJson)은 버리고 있어서** 실패
원인을 재구성할 방법이 없었다. 우선 두 곳 다 `rawJson`을 로그에 함께 남기도록
고쳤다.

이후 C13·C03을 8회 반복(48회 호출)으로 다시 돌려 재현을 시도했으나 이번엔 한 번도
재현되지 않았다 — 대략 60회 중 1회 정도로 드문 현상으로 보인다. `GeminiClient`의
`GenerationConfig`에 `maxOutputTokens` 제한이 전혀 없는 것도 확인했다(`responseMimeType`만
설정) — 배치 안 claim이 많거나 reason이 길어지면 모델 기본 출력 한도에 걸려 응답이
중간에 잘릴 수 있다는 가설은 세웠지만, 실제 잘린 응답을 아직 못 잡아서 확정할 수는
없다.

**결론**: 근본 원인은 아직 못 잡았다. 강제로 재현하려고 반복 호출을 계속 늘리는 건
비효율적이라 판단해 중단했다 — 로깅만 보강해두고, 다음에 실제로 재발하면(테스트든
운영이든) 그때 원본 응답으로 확인한다.

## GeminiClient가 일일 할당량 429를 분당 할당량 429로 오인하던 문제 수정

"AI 파트가 팀원이 pull해서 바로 쓸 만한 상태인지" 점검하다가, 이전에 겪었던 일일 할당량
소진 사고(위 "일일 무료 할당량(500회/일) 소진" 항목)의 근본 원인이 실은 안 고쳐져 있던
걸 발견했다. `GeminiClient.postWithRetry()`는 429를 잡으면 전부 같은 방식(백오프 후
최대 3회 재시도)으로 처리하는데, Gemini의 429엔 **분당 한도**(재시도 몇 초~몇십 초면
풀림)와 **일일 한도**(하루 지나야 풀림, 응답 `quotaId`가 `GenerateRequestsPerDayPer
ProjectPerModel-FreeTier`처럼 "PerDay"로 구분됨) 두 종류가 있다. 지금까지는 일일
한도에 걸려도 분당 한도인 줄 알고 최대 30초씩 3번(최대 약 90초) 헛되이 재시도한 뒤에야
실패했고, 최종 예외 메시지도 그냥 "429 Too Many Requests"라 원인 파악에 시간이 걸렸다.

`GeminiClient.isDailyQuotaExceeded(responseBody)`를 추가해 응답 본문에 "PerDay"가
있으면 재시도 없이 즉시 `GeminiDailyQuotaExceededException`(신규, 메시지에 모델명과
"하루가 지나야 복구됨"을 명시)을 던지도록 고쳤다. `GeminiClientRetryDelayTest`에 실제
운영에서 봤던 형태의 일일 한도 429 본문으로 단위 테스트 3건 추가.

### OCR 이미지 크기 상한을 엔진별로 분리 (Gemini 4MB / Vision 7MB)

4MB 상한은 원래 Gemini 실측에서 나온 값이다 — 9MB·8.4MB짜리 애니메이션 GIF 2장이 전체
용량의 80%를 차지하면서 OCR 호출을 19초까지 끌어올린 사례가 근거였다. 그런데 OCR을
Google Cloud Vision 우선으로 바꾸면서 이 근거가 Vision에는 해당하지 않는다는 게 드러났다:
**Vision은 12.3MB GIF를 1.4초에 처리했고 텍스트도 정확히 뽑았다**(애니메이션 GIF는 첫
프레임만 본다). 과금도 용량과 무관하게 장당 고정이다.

그래서 상한을 `OcrImageLoader.loadAll(urls, maxImageBytes)` 인자로 빼서 엔진별로 다르게
줬다. Vision의 7MB는 임의 값이 아니라 **JSON 요청 크기 제한 10MB**에서 역산한 값이다 —
본문을 base64로 실으면 약 1.33배로 불어나므로 원본 7MB가 실질 한계다(7 × 1.33 ≈ 9.3MB).

**남은 문제(별도 과제)**: 7MB로 올려도 12.3MB짜리 GIF는 여전히 걸러진다. 실제로 그런
이미지에서 광고 심의 대상 문구를 놓치는 걸 확인했다 — `21.gif`(860×1068, 12.3MB)를 직접
열어보니 "03 소화기능장애 / 위산 분비를 자극하여 다양한 소화기 불편함 유발"이라는, 질병
증상을 나열해 제품으로 연결하는 전형적인 구조의 콘텐츠였다.

첫 프레임만 뽑아 재인코딩하면 수백 KB로 줄어 살릴 수 있지만(`ImageIO.read`가 GIF 첫
프레임을 반환), 그대로 넣기에는 위험이 있어 별도 과제로 남긴다:

- **메모리**: `ImageIO.read`는 픽셀을 전부 메모리에 펼친다. 이전 조사에 세로 25,000px짜리
  상세페이지가 등장하는데, 1000×25,000이면 한 장에 약 100MB다. 다운로드가 동시 6개로
  돌아가므로 최악의 경우 수백 MB 스파이크가 난다 → **디코딩 전에 헤더로 해상도를 먼저 확인**해
  일정 픽셀 수를 넘으면 포기하는 방어가 필수.
- **첫 프레임에 글자가 없을 수 있음**: 애니메이션 배너는 여러 메시지를 순환한다. 지금은
  "너무 커서 제외"가 로그에 남아 누락을 인지할 수 있는데, 첫 프레임만 처리하면 "처리했는데
  빈 결과"가 되어 **알려진 누락이 모르는 누락으로 바뀐다** → 프레임 추출로 처리한 이미지는
  로그에 명시해야 한다.
- **재인코딩 포맷**: JPEG는 글자 같은 선명한 경계에 약하고, 실측에서도 리사이즈+JPEG 재인코딩이
  추출 글자수를 15~17% 떨어뜨렸다. GIF는 팔레트 기반이라 **PNG가 화질·용량 모두 유리**하다.
- **WebP 미지원**: 표준 `ImageIO`는 WebP를 못 읽어 변환이 실패한다(현재와 동일하게 제외될
  뿐이라 회귀는 아니지만, "이걸로 다 해결된다"는 기대는 맞지 않는다).

### Vision OCR 동시성을 더 올릴 수 있는가 (검토만 하고 보류)

Vision으로 바꾸면서 OCR이 11.5초에서 2초 남짓으로 줄었는데, 동시성을 8에서 더 올리면
얼마나 더 줄어드는지 계산해봤다.

**OCR 시간은 "웨이브 수 × 장당 시간"으로 거의 정확히 예측된다.** 29장을 동시 8로 돌리면
4웨이브 × 0.66초 ≈ 2.6초인데 실측이 2,631ms였다. 이 식으로 환산하면:

| 이미지 | 동시 8(현재) | 동시 16 | 동시 32 |
|---|---|---|---|
| 15장 | 2웨이브 ≈ 1.4초 | 1웨이브 ≈ 0.7초 | 0.7초 |
| 29장 | 4웨이브 ≈ 2.6초 | 2웨이브 ≈ 1.4초 | 0.7초 |
| 37장 | 5웨이브 ≈ 3.3초 | 3웨이브 ≈ 2.0초 | 1웨이브 ≈ 0.7초 |

할당량도 여유가 있다 — Vision 기본 quota가 분당 1,800건인데, 동시 8에 장당 0.66~0.71초면
분당 약 686건으로 38% 수준이다. 동시 16이어도 약 76%로 한도 안이다.

**그런데도 보류하는 이유는 병목이 이미 OCR에서 넘어갔기 때문이다.** 전체 분석 약 11초 중
OCR은 2초 남짓(18%)이고, 규칙 판정 4.7초·Claim 추출 2.3초가 더 크다. 동시성을 두 배로 올려도
전체는 1~2초 줄어드는 데 그친다(11초 → 9~10초).

게다가 올리려면 함께 손봐야 할 곳이 있다:

- **이미지 다운로드가 새 병목이 된다** — `OcrImageLoader.DOWNLOAD_CONCURRENCY`가 6이고 실측
  300~2,800ms다. OCR이 0.7초가 되면 다운로드가 OCR보다 오래 걸리는 구간이 생긴다.
- **메모리** — 동시 호출마다 base64 이미지를 들고 있다. 상한 7MB 기준 동시 32개면 순간
  약 280MB를 점유한다.

즉 "동시성 숫자만 올리면 되는" 작업이 아니라 다운로드 동시성·메모리까지 같이 봐야 하는데,
얻는 게 1~2초라 우선순위가 낮다. 같은 노력이라면 규칙 판정(4.7초) 쪽이 효과가 크다.

### 병목은 고정돼 있지 않다 — OCR → 규칙 판정 → Claim 추출로 옮겨간 기록

분석 1건이 20.5초(중앙값)였고 그중 OCR이 11.5초(44~65%)라 OCR부터 손댔는데, 고치고 나니
병목이 다음 단계로 옮겨갔다. 세 번에 걸쳐 "가장 느린 곳"이 바뀐 과정을 남겨둔다.

| 단계 | 시작 시점 | OCR 교체 후 | 동시성 조정 후 |
|---|---|---|---|
| OCR | **11.5초 (최대)** | 1.4~2.6초 | 1.4~2.6초 |
| 규칙 판정 | 4.7초 | **5.6~6.2초 (최대)** | **2.9초** |
| Claim 추출(AI#1) | 2.3초 | 2.3초 | **2.3초 (최대)** |
| 전체 | 20.5초 | 약 11초 | 약 7~8초 |

**1) OCR — 엔진을 바꿔 해결.** 무료 티어 분당 15회 제약 때문에 이미지 10장 묶음·동시 3으로
묶여 있었는데, 이 제약을 없애려고 청크 크기·이미지 리사이즈·모델 교체를 차례로 실측했으나
전부 기각됐다(각 항목의 근거는 위 절들과 코드 주석에 있다). 결국 OCR만 Google Cloud Vision으로
옮겨 "요청 1건 = 이미지 1장"을 동시 8로 던지는 구조가 됐다.

**2) 규칙 판정 — 같은 호출 수로 시간만 절반.** 여기서 중요한 구분이 하나 있었다. 규칙 판정
5.9초를 "LLM 추론이라 못 줄이는 시간"으로 봤는데, 뜯어보니 그렇지 않았다:

```
호출 12회 ÷ 동시성 4 = 3웨이브 × 개별 1.2~2.5초 ≈ 5.4초
                       ↑ 이 중 약 2/3가 줄서기이지 추론이 아니었다
```

규칙끼리는 완전히 독립적이라 한꺼번에 던져도 판정 내용이 바뀌지 않는다. 동시성을 12로 올려
동일 입력으로 비교하니 **규칙 판정 5,921ms → 2,864ms(-52%), 전체 8,124ms → 5,024ms(-38%),
Gemini 호출은 15회로 동일, 429도 0건**이었다.

동시성이 quota에 중립인 이유도 여기서 분명해졌다 — 분당 한도는 "1분에 몇 번 불렀나"를 보므로,
동시성을 올려도 분석 1건이 쓰는 호출 수는 그대로다. 실제로 이 작업 중에 관찰된 429는 동시성이
아니라 **분석을 30초 간격으로 연달아 돌려서** 났다(분석 2건이면 같은 분에 24~26회).

**3) 남은 최대 항목은 Claim 추출(2.3초)인데, 이건 구조상 줄이기 어렵다.** 페이지 전체 텍스트를
한 번에 보는 단일 호출이라 병렬화할 대상이 없다. 쪼개서 병렬로 돌리면 문맥이 끊겨
"이 문장이 제품 효과 주장인지"를 판단하는 근거가 사라진다.

**교훈**: "어디가 느린가"만큼 **"왜 느린가"를 구분하는 것**이 중요했다. 같은 5.9초라도 추론
시간이면 손댈 수 없지만 줄서기면 스케줄링만 바꿔 절반으로 줄어든다. 처음엔 규칙 판정을 전자로
잘못 짚었고, 웨이브 수로 분해해보고 나서야 후자인 걸 알았다.
